================================================================================
VV DESIGNER - REAL SKETCH EXAMPLES (vv-fbx-sketch format)
================================================================================

WHAT THIS IS
  Eight complete sketch files - seven real production exports (2026-07-08, via
  the Logic Designer Import/Export userscript) plus one authored, validated
  template (example 8) - and the notable single-block shapes from larger
  production sketches, combined into one file so an AI agent can learn the
  EXACT structure of a valid VV sketch.

  Every JSON document under an "EXAMPLE n" heading passes validate-vv-sketch.js
  (examples 1-7 are verbatim production data): save one as a .json file and it
  imports as-is (File -> Transfer -> Import sketch (JSON) on the VV Designer,
  internal.iwmac.local/vv_fbx.qxs).

HOW TO USE THIS FILE (for an AI generating a sketch)
  1. Read AI-BRIEFING.txt (same folder) for the full rules. This file shows
     what correct output LOOKS like; the briefing says what is allowed.
  2. Pattern-match the request to the closest EXAMPLE below and copy its
     structure. Change only ids/coordinates/data values/driver ids - never
     invent new field names, block types, or a different overall shape.
  3. Emit PURE JSON: no comments, no trailing commas, integer block ids.
  4. Validate before delivering:
       node logic-designer-import-export/validate-vv-sketch.js <your-file>.json
     Exit 0 = importable. Fix every reported error.

THE ENVELOPE (annotated skeleton - the comments here are ILLUSTRATION ONLY;
a real file must be pure JSON with no comments)

  { "format": "vv-fbx-sketch",          <- required marker, exactly this string
    "version": 1,
    "exported_at": "<ISO 8601>",
    "source_plant_id": "5290" | null,   <- null for generated files
    "source_sketch_id": "6959" | null,
    "name": "<short name>",
    "block_count": N,                   <- must equal sketch.blocks.length
    "connection_count": M,              <- must equal sketch.connections.length
    "sketch": {
      "mode": "function",               <- REQUIRED ("process" only for reusable sub-sketches)
      "require_plant_revision": 0,      <- 620 if IF / WEATHER / AGE_OF_VALUE used
      "blocks": [ ... ],                <- see block anatomy below
      "connections": [ ... ],
      "groups": [] } }                  <- [] in every production file

BLOCK ANATOMY (every block has ALL of these keys)

  { "id": 0,                            <- INTEGER, unique, 0,1,2,...
    "func": "paramv",                   <- exact lowercase block_func; copy from an example of the same type
    "type": "PARAMV",                   <- exact UPPERCASE palette key
    "compile_type": "input",            <- input | function | condition | output | process
    "data": { ... } | null,             <- per-type snake_case payload; null = user configures after import
    "override": {"alias_text":"label"} | {},   <- the on-canvas label lives HERE
    "runtime": {},
    "properties": [],                   <- [] when empty; set entries are {"<name>":{"alias_text":"...","value":...}}
    "output_type": ["mixed"],           <- copy from a same-type example
    "x": 90, "y": 90 }                  <- canvas px; lay out left->right by dataflow

CONNECTION ANATOMY

  { "source": { "id": 0, "put": 0 },    <- source block id + its OUTPUT pin index (0-based)
    "target": { "id": 1, "put": 0 },    <- target block id + its INPUT pin index (0-based)
    "alias_text": "Input 1" }           <- optional; real exports carry the target pin's name.
                                           Period/age blocks add "by_refference": true on target.

TEN THINGS EVERY REAL FILE SHOWS (check your output against each)
   1. Block ids are integers - never strings. Pins are numeric indices - never names.
      Ids need only be UNIQUE - production files have gaps from deleted blocks
      (see example 6); generated files should just use 0,1,2,...
   2. Every block carries "func", and it exactly matches its "type".
   3. All data fields are snake_case host names: driver_ids, initial_value,
      alias_text, force_write, block_func_args, alarm_destination, ...
   4. PARAMV/WRITETOUNIT bind via FULL parameter driver ids, pattern
      <plant>_<driverType>_<unit>_..._<param> (e.g. "10111_AKPC420_CC350_0_110_0_4_2001").
      NEVER invent one. If the user did not supply it: "data": null +
      "override": {"alias_text":"TODO bind: <what>"} - the block imports red and
      the user binds it in the designer.
   5. WRITETOUNIT writes REAL hardware. data always {"force_write":false,"delay":0,
      "limit_count":false,"count":1,"driver_ids":[...]}; several ids fan the same
      value out to many parameters. Only include this block when the user asked to write.
   6. CONST data always carries "values": null, plus "type" + "initial_value"
      (+ "precision" like "%.1f" for floats; string CONSTs have a string initial_value).
   7. One wire max per input pin; outputs fan out freely.
   8. override/runtime empty are {}; properties empty is [] (host style; {} also accepted).
   9. sketch.groups is [] in every production file.
  10. Every operation is a block + wires. There is NO expression language, NO steps,
      NO parameterBindings - the only expression-like string in VV is INSIDE a
      FORMULA block's data.formula (inputs inp0, inp1, ...).

EXAMPLE 1 - PARAMETER BRIDGE (the most common production sketch: 2 blocks, 1 wire)
================================================================================

Source: vv-sketch_10111_Lysbryter-til-Disker_20260708-1028.txt (plant 10111), 2 blocks / 1 wires.
Copies a light-switch digital input onto two case controllers.

What it teaches:
  - The smallest valid file: one PARAMV read wired straight into one WRITETOUNIT.
  - WRITETOUNIT with TWO driver_ids = the same value written to many parameters ("Multiple parameters").
  - PARAMV data is exactly {"driver_ids":["<full driver id>"]} - nothing else.
  - WRITETOUNIT data is exactly {"force_write":false,"delay":0,"limit_count":false,"count":1,"driver_ids":[...]}.

Blocks:
  id 0: PARAMV "U110, Maskinrom, u10 DI1 status  "
  id 1: WRITETOUNIT "Multiple parameters"
Wiring (source output -> target input):
  PARAMV(0) out0 -> in0 WRITETOUNIT(1)   pin name: "Input 1"

EXAMPLE 5 - FORMULA + VIRTUALOUT (compute a value and store it as a virtual parameter)
================================================================================

Source: vv-sketch_9652_Driftmode-360-01_20260708-1450.txt (plant 9652), 3 blocks / 2 wires.
Maps a ventilation operating-mode parameter through a formula and stores the result.

What it teaches:
  - FORMULA data: {"formula":"...","title":"...","output_type":"integer","eng_unit":""} - inputs are inp0, inp1, ... inside the formula string. This is the ONLY place anything expression-like exists in VV.
  - VIRTUALOUT data: {"alias_text":"...","type":"integer","engineering":{"unit":""}} - the safe output block (creates a trendable virtual parameter, writes no hardware).

Blocks:
  id 0: PARAMV "V01, 360.01 Ventilasjon, DriftMode [ Current DriftMode 000-099:Agg Stop 100-199:Agg Lo Speed 200-299 ]"
  id 1: FORMULA "Driftmode"
  id 2: VIRTUALOUT "360.01 Driftmode"
Wiring (source output -> target input):
  PARAMV(0) out0 -> in0 FORMULA(1)   pin name: "Input"
  FORMULA(1) out0 -> in0 VIRTUALOUT(2)   pin name: "Input 1"

--- REAL PRODUCTION FORMULAS (fleet scrape, 87 plants / 71 unique formulas - grammar reference) ---
All of these are deployed on live plants and use only the documented grammar:
  inp0==2                                     (mode decoder)
  inp0/3600                                   (HOURMETER seconds -> hours)
  inp0/(3600*24)                              (seconds -> days)
  (inp0*-1)+1                                 (boolean negation)
  (date('W', time()) % 2 == 0) ? 1 : 0        (even ISO week - biweekly gating)
  (inp1-inp0)*inp2*inp3/3600*1000             (energy calculation)
  (inp0>=0&&inp0<=99?0:(inp0>=100&&inp0<=199?1:(inp0>=200&&inp0<=299?2:5)))
                                              (chained ternary range mapping; && works)
The server evaluator is PHP, so production also uses PHP stdlib + null:
  (intval(inp0) == 1) ? 0 : ((intval(inp0) == 2) ? 1 : null)   (null = write nothing)
  strpos(inp0, inp1) !== false ? true : false                  (substring test)
  stripos(inp0, 'snø')!==false?true:false                      (case-insensitive - weather text)
  substr(inp0, 0, 8)                                           (string slice)
  floatval(inp0/60.0)                                          (kW -> kWh unit math)
  idate("H")                                                   (current hour as int)
  (abs(time() - strtotime(inp0)) <= inp1/2) ? 1 : 0            (timestamp freshness)
  gmdate("H:i:s", inp0*3600)                                   (seconds -> H:i:s text)
  inp0*floatval(rand(-10,10))                                  (PHP two-arg rand)
  inp0 == 1 AND inp1 == 0                                      (uppercase AND works)
THE state MAGIC VARIABLE - a formula can reference its OWN PREVIOUS OUTPUT:
  (inp0 >= inp1 ? 1 : (inp0 < inp2 ? 0 : state))
  = complete changeover/hysteresis in ONE formula block: output 1 when inp0 is
  at/above the high limit (inp1), 0 when below the low limit (inp2), otherwise
  HOLD the previous output. The formula-level alternative to a LATCH block.
Server-only VV domain built-ins also exist (calendar-schema helpers - a client
evaluator cannot resolve these): is_calendar_deviating(14), value_based_on_schema(1,0,14).
Full-PHP wizardry is possible server-side (won't simulate locally) - the fleet's
Legionella scheduler computes the day-of-month of the month's LAST SUNDAY:
  date('d', strtotime(implode(' ', ['last sunday of', date('M')])))
FORMULA INVARIANT: properties.input_count = {"alias_text":"Input count","value":N}
where N EQUALS the wired-input count - true for 530/530 production formulas and
enforced by validate-vv-sketch.js. Without it extra pins do not exist.

emitting a boolean for one state ("inp0==K"); each boolean then gates its own

================================================================================
HOW BIG PRODUCTION SKETCHES ARE BUILT
================================================================================

The largest corpus sketches are small recipes REPEATED, not new structures:

  - "switch-funksjon" (88 blocks / 80 wires): the same stamp eight times - one
    library process fed by seven CONSTs, its outputs into three WRITETOUNITs.
  - "switch-endedisker" (44 blocks): the identical stamp four times.
  - "COPonline-KA1" (22 blocks): ONE process + 15 PARAMV readings + 6 CONSTs
    wired into its pinned inputs.
  - "init-oppsett" (28 blocks): four different library processes, each fed by
    PARAMV / CONST / CALENDAR blocks on their required inputs.

HOW PRODUCTION LOGIC IS ARCHITECTED (deep-dive census, 138 plants / 1508
sketches / 37,503 blocks / 36,970 wires, 2026-07-11):

  - Three archetypes: PROCESS-HUB (a library process + only feeders/outputs)
    26% of sketches; PURE BLOCK LOGIC (no processes) 38%; MIXED 35%.
  - Logic is SHALLOW and WIDE: 71% of sketches have a longest path of <= 4
    blocks. Big sketches grow by stamping parallel rows, never deep chains.
    84% of outputs feed exactly one input. Median sketch: 11-20 blocks.
  - Top motifs by occurrence: process -> WRITETOUNIT (1341), process ->
    VIRTUALOUT (938), gated write IF -> WRITETOUNIT (839), parameter bridge
    PARAMV -> WRITETOUNIT (515), setpoint select SELECTOR -> write (497).
  - IF is an ENABLE SWITCH more than a computed gate: 69% of IF condition
    pins are fed by a labelled boolean CONST the customer can flip - not a
    comparator. Reproduce this: gate switchable behaviour on a named CONST.
  - Alarms are debounced: comparator -> DELAY/DELAY_VARIABLE -> ALARM is the
    standard chain (direct comparator -> ALARM is rare).
  - The canonical process hub: one process instance with pins fed by CONSTs
    (10,926 wires fleet-wide) + PARAMVs (5,191); TRANSFORM_MAPPED converts
    pressure -> temperature BEFORE the process pin when needed (454).
    Processes chain process -> process (68).
  - Templates are stamped byte-identically across plants: the 2-block
    PARAMV -> WRITETOUNIT bridge is a named template on 13 plants; kurve-
    styring/sandstadkurve 44-63-block stamps ~86x across 8 plants; the Yr
    weather-data sketch on 12 plants.
  - Process instance type keys can be PURE WORDS with no uniqid segment
    (EW_VENTILATION_ROOM_TEMPERATUR_HIGH_LIMIT) - treat any
    compile_type "process" type as an opaque key that must exist in the
    target plant's library.

PRODUCTION DEFAULTS (field-level census, 191 plants / 50,443 blocks):

  - ALARM pri: "a" is the fleet norm (79%; c 15%, b 6%); destination
    "general" 91%. Default to a/general unless the user says otherwise.
  - WRITETOUNIT: force_write false (true is 2.6%), delay 0 (two exceptions
    fleet-wide), limit_count false, count 1. Emit exactly these.
  - CONST: float is the most common type (float > integer > boolean >
    string); mode "single" essentially always (repeat is 29 of 15,774).
  - LABEL EVERY BLOCK: 73% of all production blocks have override.alias_text
    set. Older sketches may OMIT data keys entirely - when READING, treat a
    missing key as its default; when GENERATING, write keys explicitly.
  - eng_unit vocabulary: &deg;C (HTML entity - most common!), °C, %, min, K,
    sek, kWh, ppm, Pa. Entity and literal degree forms are interchangeable.
  - by_refference wires (the "read value by reference" pin flag) cluster on:
    PARAMV -> AVG/MIN/MAX_IN_PERIOD.put0, comparator -> DELAY.put0,
    SUBTRACT -> TRANSFORM_MAPPED.put0 (superheat into refrigerant map), and
    OPTIMAL_START_STOP wiring: put0 <- CALENDAR_2_0 (by_ref), put2 <- PARAMV,
    puts 3-5 <- CONSTs.
  - When READING production sketches, expect clutter: 27% of sketches contain
    unwired helper blocks (leftover CONSTs, parked readings) - not an error.
    Generated sketches should still wire everything.
  - groups is [] in nearly every sketch, but NON-EMPTY groups exist (visual
    group boxes: {id, blocks:["<string ids>"], alias_text, open, box}) -
    preserve them when editing an existing sketch; emit [] for new ones.
  - Sketch NAMES read like drawing labels in the plant's language:
    "Kurvestyring", "Yr.no", "360.001 Sandstadkurve", "+01=360.009_Kurve".
  - DELAY_VARIABLE's delay pin is usually a CONST but 47 production sketches
    compute it with a FORMULA (dynamic delay) - allowed. PULSE_COUNT's level
    pin is CONST-only (host-enforced), 17/17 in the fleet.

Corpus-wide block frequency: CONST 8394+, PARAMV 5599+, WRITETOUNIT 2875+,
VIRTUALOUT 1658+, then FORMULA / IF / DELAY_VARIABLE - and almost no ALARMs.
Production VV logic mostly CONTROLS (writes values); it does not just alarm.
ZERO block types outside the documented allowlist appeared in the entire
fleet corpus (37,503 blocks). Binding split at scale: singular driver_id 3331
vs plural driver_ids 2155 on PARAMV (WRITETOUNIT 1501 vs 1311) - legacy
singular is the MAJORITY, so always READ both, GENERATE plural.
