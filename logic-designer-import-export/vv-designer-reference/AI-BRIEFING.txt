--------------------------------------------------------------------------------
1. WHAT THE VV DESIGNER IS
--------------------------------------------------------------------------------
The VV Designer ("Virtual Values Designer") is IWMAC/Kiona's visual
function-block editor for refrigeration/energy plants. A user builds a
"sketch": a dataflow graph of typed blocks wired output-pin to input-pin,
like a PLC function block diagram. The sketch is saved on a plant, compiled
server-side, and deployed to that plant's controllers, where it runs
continuously: reading live parameters, computing, raising alarms, storing
virtual values, and (optionally) writing setpoints back to hardware.

Key vocabulary:
- Plant: one installation (identified by plant_id, e.g. 5440). Everything is
  plant-scoped.
- Sketch: one logic graph. The deployable unit.
- Block: one node. Its "type" is an UPPERCASE palette key (e.g. PARAMV,
  BIGGERTHAN, ALARM). Each type has fixed input/output pins.
- Pin ("put"): a numeric, 0-based connection point. Inputs are on the left of
  a block, outputs on the right. Outputs may fan out to many inputs; EACH
  INPUT ACCEPTS EXACTLY ONE WIRE.
- Connection: a wire from one block's output pin to another block's input pin.
- Parameter / driver id: a real data point on the plant, identified by a full
  driver id string such as "5440_AK3_AKC_0_1_0_0_2576". The leading digits are
  the plant id. NOTE: a unit id like "000:001" is a UNIT (a device holding
  many parameters) — it is NOT a parameter and can never be used as a binding.
- Process: a published, reusable sub-sketch that appears as a single block.
  Only relevant if the user explicitly names one.

THE SINGLE MOST IMPORTANT FACT: there is NO expression language, NO script,
NO "steps", NO conditions-as-text. Every operation — every comparison, every
AND, every alarm, every write — is a separate BLOCK, and every data flow is a
WIRE. If you find yourself writing an expression string like
"enable && temp > limit", stop: that must become a CONST block, a comparator
block, a COMP_AND block and wires.

--------------------------------------------------------------------------------
2. THE OUTPUT FILE — EXACT SHAPE (NORMATIVE)
--------------------------------------------------------------------------------
Emit ONE pure JSON file. No comments (// or /* */ make the file unparseable),
no trailing commas, no placeholders outside the rules below.

{
  "format": "vv-fbx-sketch",
  "version": 1,
  "exported_at": "<ISO8601 timestamp>",
  "source_plant_id": null,
  "source_sketch_id": null,
  "name": "<short descriptive name>",   <- name it like a technician labels a
                                            drawing, in the plant's language:
                                            "Kurvestyring", "Snøsmelt styring",
                                            optionally a drawing-number prefix
                                            ("360.001 Kurvestyring")
  "block_count": <integer, must equal sketch.blocks.length>,
  "connection_count": <integer, must equal sketch.connections.length>,
  "sketch": {
    "mode": "function",
    "require_plant_revision": 0,
    "blocks": [ <block>, ... ],
    "connections": [ <connection>, ... ],
    "groups": []
  }
}

"mode" is REQUIRED and is "function" for normal plant logic ("process" only
when explicitly building a reusable process). Omitting mode = instant
rejection ("Sketch document is malformed").

<block> — every block object has EXACTLY these fields:

{
  "id": 0,                          // INTEGER, unique, 0,1,2,... NEVER a string
  "type": "BIGGERTHAN",             // UPPERCASE palette key from section 4 ONLY
  "func": "biggerthan",             // copied VERBATIM from section 4 — never omit
  "compile_type": "function",       // from section 4
  "data": { ... } | null,           // per-type payload from section 4, or null
  "override": {},                   // or {"alias_text": "<canvas label>"}
  "runtime": {},
  "properties": {},
  "output_type": "boolean",         // from section 4 (informational)
  "x": 260, "y": 110                // numeric canvas coordinates — REQUIRED
}

- The on-canvas label lives in override.alias_text. There is no "name" or
  "label" field on a block.
- override, runtime, properties are BLOCK-LEVEL fields, siblings of "data".
  They NEVER appear inside data.
- "func" is applied verbatim on load; omitting it breaks the compiled sketch.
- Lay out x/y left-to-right by dataflow: sources x≈40, logic x≈260-500,
  outputs x≈700; stack parallel branches ~150 px apart vertically.

<connection> — every wire has EXACTLY this shape:

{ "source": { "id": 0, "put": 0 }, "target": { "id": 2, "put": 0 } }

- source = the block whose OUTPUT the wire leaves; target = the block whose
  INPUT it enters. "put" is the 0-based pin index on that side.
- There are NO named pins. Keys "from", "to", "block", "pin", "output",
  "input" DO NOT EXIST in this format and cause rejection.
- Each target (id, put) pair may appear at most once across all connections.
- Wire EVERY non-optional input of every block you place.

ALLOWLIST SEMANTICS: only the keys shown in this section and the data fields
shown in section 4 exist. If a key is not listed here, it does not exist. Do
not invent, rename, camelCase, or "improve" any field name. This allowlist is
validated at fleet scale: a 2026-07 scrape of ~191 plants / ~1889 production
sketches (50,443 blocks) contained ZERO block types outside it.

LABEL EVERY BLOCK: set override.alias_text on each block you generate (what
the block does, in the user's language). 73% of all production blocks are
labelled - an unlabelled sketch reads as machine-generated noise.

WHEN EDITING AN EXISTING SKETCH (vs generating new): block ids are NOT
compact in production (70% of sketches have id gaps from edit history) -
NEVER renumber existing ids; new blocks get max(id)+1. Saved wires all carry
an "alias_text" pin label (the host stamps them on save - you may omit them
in generated files). Non-empty "groups" (visual boxes) must be preserved.
Hard rules production never violates: no self-loops, no duplicate wires,
one wire per input, integer ids, non-negative x/y.

--------------------------------------------------------------------------------
3. THE TYPE SYSTEM (WHY WIRES ARE ACCEPTED OR REFUSED)
--------------------------------------------------------------------------------
Values on wires are boolean, integer, float, string, or mixed. Inputs accept
widened types: an input declaring "float" accepts boolean/integer/float; an
input declaring "string" or "mixed" accepts everything. Comparator and logic
blocks output boolean. Arithmetic blocks output float.

Two additional constraints:
- Some inputs demand a specific SOURCE BLOCK TYPE (require_type). Example:
  PULSE_COUNT's input 1 ("Logic True Level") must be fed by a CONST block.
- TAGVALUE blocks can ONLY feed process blocks (their output carries
  require_type "process"). For ordinary logic, the general reader is PARAMV.
  Never use TAGVALUE unless wiring a published process's pinned tag input.
- PROCESS INSTANCES (compile_type "process"): opaque library blocks - copy
  type/func verbatim; they must exist in the target plant's library. Their
  pins are mostly constant-settings (feed with CONSTs). Many processes have
  ZERO outputs (the alarm/write lives INSIDE the process) - an instance with
  no outgoing wires is normal production logic, not an error.

4. BLOCK REFERENCE — THE ALLOWLIST
--------------------------------------------------------------------------------
Copy type / func / compile_type / data EXACTLY. "data: null" means the block
needs no configuration (or is deliberately left for the user to bind after
import — it then shows a red title until configured in the designer).

READERS AND SOURCES (compile_type "input")
- PARAMV  | func "paramv"
  Reads one plant parameter. data: {"driver_ids": ["<FULL_DRIVER_ID>"]}
  driver_ids is a NON-EMPTY ARRAY of full ids. If you do not know the real id,
  set data: null and override.alias_text "TODO bind: <description>" — never
  invent an id, never emit an empty array.
  output_type: ["mixed"]
  (When READING/analysing an existing sketch: legacy singular
  {"driver_id": "<id>"} is the MAJORITY in the fleet — accept both forms,
  but always GENERATE the plural array.)
  ID ANATOMY (27,860 fleet ids): usually 8 underscore-separated segments,
  "<plant>_<DRIVER-INSTANCE>_<device>_...". Only the "<plant>_" prefix is a
  reliable contract - device names may contain underscores, and the driver
  token is an INSTANCE name (AK3, AK2, BACNET...BACNET10, MODBUS2, KNX, JC,
  CORRIGO34, VIRTUAL, VIRTUELL), not a fixed vocabulary. NEVER parse,
  construct, or "correct" an id - copy it verbatim from the user/plant.
  An id whose plant prefix differs from the target plant reads NOTHING
  (69 such never-rebound ids exist in production - a real failure mode).
- CONST   | func "const"
  A user-editable constant (limits, setpoints, levels). data:
  {"alias_text": "<name>", "type": "integer"|"float"|"boolean"|"string",
   "initial_value": <value>, "mode": "single", "eng_unit": "<unit or ''>",
   "readonly": false}
  Add "precision": "%.1f" (or %.2f/%.3f) only when type is float.
  output_type: ["boolean","integer","float","string"]
  Common production eng_units: &deg;C (HTML entity form is the most common!),
  °C, %, min, K, sek, kWh, ppm, Pa - both entity and literal degree forms
  are real; '' is fine for unitless.
- CALENDAR | func "calendar_value" — boolean from a plant calendar schedule.
  data: {"calendar": "<id>", "offset": 0, "post_offset": 0} or null (TODO bind).
- CALENDAR_2_0 | func "calendar.run" — newer calendar. Production data:
  {"calendar": "<id>", "output": "id"} — or null to bind later.
- DATE_TIME | func "vv_datetime.run" — clock outputs. data {"units": [<idx>...]}
  picks which outputs exist: 0=Year 1=Month 2=Day 3=Hour 4=Minute 5=Second
  6=Weekday; add matching properties output_count + output_alias_texts
  (e.g. {"units":[3]} + output_count 1 + ["Hour"]).
- CRITERIA | func "criterias.run" — boolean from date/time ranges (year, month,
  week, day-of-week, hour, minute). Configure post-import (data null).
- TOGGLE_INTERVAL | func "toggle_interval.run" | data
  {"block_func_args":{"interval":"sec|min|hour|day|week|month|year","offset":0}}
  (offset = whole seconds; exactly these two keys). SYMMETRIC square wave only:
  the output flips at each interval boundary. There is NO duration/duty field,
  so "X hours every N days" is NOT expressible with this block - gate on a
  plant CALENDAR (recurring schedule) for asymmetric windows instead.
- WEATHER | func "weather.run_by_ccp_country" and WEATHER_SUN | func
  "weather_sun.run_by_place" — YR.no weather / day-night. WEATHER_SUN data:
  {"block_func_args": {"rise_offset": 0, "set_offset": 0}} (minutes around
  sunrise/sunset). WEATHER data: {"block_func_args": {"func": "<one of:
  current_temperature | current_precipitation | current_dew_point |
  current_humidity | highest_temperature | lowest_temperature | symbol_text
  | symbol_number | current_wind | forecast>", "period_count": 1}}.
- SPOT_PRICE family — electricity spot prices; region is an ENTSO-E zone code:
  SPOT_PRICE "spotprice.run": {"hours": [0], "region": "10YNO-3--------J"}
  SPOT_PRICE_LOW "spotprice.run_is_low_price" / SPOT_PRICE_HIGH
  "spotprice.run_is_high_price" (boolean: now among the cheapest/priciest
  percent% of the next N hours; STRING numbers):
  {"region": "10YNO-3--------J", "percent": "30", "num_future_hours": "12"}
  SPOT_PRICE_NUM_HOURS "spotprice.run_get_num_hours": {"region": "<zone>"}
  SPOT_PRICE_ANALYSER "spotprice.run_analyse".

COMPARATORS AND LOGIC (compile_type "function", output boolean, 2 inputs each
unless noted, data null)
- BIGGERTHAN "biggerthan", BIGGERTHANOREQUAL "biggerthanorequal",
  SMALLERTHAN "smallerthan", SMALLERTHANOREQUAL "smallerthanorequal"
- LIKE "like" (equality), UNLIKE "unlike" (inequality)
  THERE IS NO "EQUAL" BLOCK. Equality is LIKE.
- COMP_AND "comp_and", COMP_OR "comp_or" (expandable inputs; wire i0,i1,...)
- INVERT "invert" (1 input, boolean NOT)

ARITHMETIC (compile_type "function", output float, data null)
- ADD "add", SUBTRACT "subtract", MULTIPLY "multiply", DIVIDE "divide",
  MOD "mod", AVERAGE "average", MIN "comp_min", MAX "comp_max",
  DIFF "diff" (abs difference), ABSOLUTE "absolute" (1 input)

TIME / PERSISTENCE / MEMORY
- DELAY_VARIABLE | func "alarm_multi_delay" | data null
  "Condition must hold N seconds before output goes true." Inputs: put 0 = the
  boolean/value; put 1 = the delay in SECONDS (required) - usually a CONST,
  but a FORMULA output is also production-valid (dynamic delay, 47 fleet-wide);
  put 2 = optional CONST delay-when-false. Best debounce block for generated
  logic. (PULSE_COUNT put 1 is different: CONST-only, host-enforced.)
- DELAY | func "alarm_multi_delay" — same idea but delay set in a dialog;
  prefer DELAY_VARIABLE.
- AGE_OF_VALUE "age_of_value", DELTA_T "delta_t" — age of a value.
- LATCH | func "latch.run" | data null — set/reset memory: put 0 = set,
  put 1 = reset, output holds 1 until reset.
- HOURMETER "hourmeter.run" — accumulated run time of a boolean.
- PULSE_COUNT | func "pulse_count"
  Counts events on a signal within a configured period. data:
  {"block_func_args": {"periode": "day", "type": "flank_rising_edge",
    "periode_amount": 1}}
  periode: "sec"|"min"|"hour"|"day"|"week"|"month"|"year"
  type: "over_or_equal_value" | "absolute_value" | "flank_rising_edge" |
        "flank_falling_edge" | "flank_changing_edge"
  (so rising/falling-edge counting is NATIVE — via "type", NOT "mode")
  Inputs: put 0 = the signal; put 1 = a CONST "Logic True Level" (REQUIRED,
  must be a CONST source). The count RESETS each configured period — there is
  no "never reset".
- PERIODE_VALUE ("Counter Limit") | func "counter_limit.run"
  data: {"block_func_args": {"mode": "alarm"|"value", "periode": "day",
  "period_amount": 1}}. NOTE the inner keys differ from PULSE_COUNT.
- AVG_IN_PERIOD "avg_in_period": data {"block_func_args": {"period": "min",
  "period_amount": 5}} — note this one uses "period" (no e).
  Also MIN_IN_PERIOD "min_in_period", MAX_IN_PERIOD "max_in_period",
  SUM_IN_PERIOD "sum_in_period".
  The block_func_args key sets are per-type host contract — copy them exactly;
  do not normalize the periode/period spelling differences.

SELECTION AND MATH EXPRESSIONS
- SELECTOR | func "selector" — 3 inputs: put 0 boolean condition, put 1 value
  if true, put 2 value if false. Build the two alternatives as CONST blocks.
- INPUT_SELECTOR "selector_ex.run" — biggest/smallest/indexed of many inputs.
- FORMULA | func "formula"
  The ONLY place any expression exists, and it is server-side PHP math over
  named inputs inp0..inpN-1 (N = number of wired inputs):
  data: {"formula": "inp0*1.8+32", "output_type": "float", "title": "<name>",
         "precision": "%.1f"}
  Allowed: + - * / % ^, comparisons (== for equality), ternary ?:,
  and/&&/or/|| (uppercase AND/OR also works), null in ternary branches
  (null result = write nothing), and functions min max abs round floor ceil
  sqrt pow sin cos log log10 exp fmod pi() random() time()
  date('w|W|N|G|H|i|s|j|d|n|m|Y|y|z|U'). PHP stdlib also works (the evaluator
  IS PHP; all production-verified): intval(x), floatval(x), idate('H'),
  substr(s,a,b), strpos(haystack,needle) !== false, stripos(...) (case-
  insensitive), strtotime(s), rand(min,max), gmdate(fmt,ts). SPECIAL: the variable `state`
  = the formula's own PREVIOUS output — production changeover/hysteresis in
  one block: (inp0 >= inp1 ? 1 : (inp0 < inp2 ? 0 : state)).
  NOT allowed: if(){} blocks, named constants (pi, e), variables other than
  inp0..inpN-1 and state. Prefer plain arithmetic blocks for trivial math;
  formulas beyond the documented set cannot be locally simulated before deploy.
  A FORMULA with more than one input MUST declare
  properties.input_count = {"alias_text": "Input count", "value": N} where N
  EQUALS the number of wired inputs (fleet invariant, 530/530 production
  formulas; the validator enforces it) - without it, extra input pins do not
  exist and wires to them are silently dropped.
- TRANSFORM_MAPPED "transform_mapped.run" — value-mapping tables. In
  production 95% use a CUSTOM table (func becomes
  "transform_mapped_custom.run", data.block_func_args.map = "__custom__",
  table in properties.custom_transform_map = {alias_text, value:
  {inputs:[[from,to],...], output:[from,to]}}); named refrigerant maps
  (co2_enthalpy, suva_404a, ...) are rare. Typical use: superheat/pressure
  -> temperature before a curve process.

OUTPUTS (compile_type "output" unless noted)
- ALARM | func "alarm"
  data: {"alias_text": "<alarm text>", "pri": "a"|"b"|"c",
         "alarm_type": "general"|"system",
         "alarm_destination": "general"|"ew"|"cw"}
  ONLY priorities a/b/c exist (a = most severe). There is no "n", no "info",
  no "severity", no "message" field. Fleet norm: pri "a" is 79% of all
  production alarms (c 15%, b 6%); destination "general" is 91%. Pick by the
  user's intent, but "a" + "general" is the production default.
  ALARM TEXT STYLE (1,609 fleet texts): "<drawing/tag number> <fault>", in
  the plant's language - "360.003 Ingen Kommunikasjon I/O Modul Nr.3",
  "Høyt diff.trykk RD40 320.01". Short fault statements, not sentences;
  include the user's equipment/drawing reference when given.
- ALARM_OBJECT "alarm_object" (adds a cost input), ALARM_OBJECT_EXTENDED
  "alarm_object_extended" (cost/value/limit inputs) — same data shape.
- VIRTUALOUT | func "virtualout"
  Stores the input as a new virtual parameter (trendable, safe). data:
  {"alias_text": "<name>", "type": "integer"|"float"|"boolean",
   "engineering": {"unit": "<unit or ''>"}}  (+ "precision" for float)
  CROSS-SKETCH PIPELINES: a VIRTUALOUT's value becomes a plant parameter
  other sketches read with a plain PARAMV (driver id contains _VIRTUAL_).
  This is first-class fleet architecture: 21% of ALL production sketches
  read another sketch's virtual output; 46% publish one. To split big logic,
  chain sketches this way instead of building one giant sketch.
- WRITETOUNIT | func "set_unit_value" | compile_type "function"
  WRITES TO REAL HARDWARE when deployed. data: {"force_write": false,
  "delay": 0, "limit_count": false, "count": 1,
  "driver_ids": ["<FULL_DRIVER_ID>"]}
  These values ARE the fleet defaults (force_write true is 2.6% of production,
  delay is 0 in all but two blocks fleet-wide, count is 1) - emit exactly
  these; several driver_ids in one block fan the same value out to many
  parameters. Production often throttles writes with the block-level
  property interval = {"alias_text": "Interval", "value": "10 sec"} (978
  fleet blocks) - optional, add when the user wants periodic rewriting.
  Include this block ONLY if the user explicitly asked to write to hardware
  AND supplied/confirmed the exact target parameter. Otherwise use VIRTUALOUT.
- TEMP_VALUE "tmp_value" — persist and pass through a value. Production data:
  {"alias_text": "<name>", "type": "mixed", "precision": "%.1f"}
- VARIABLE_OUTPUT "variable_output" / VARIABLE_INPUT "variable_input" — named
  reference pair to reuse a value elsewhere in the same sketch (feedback
  without a wire). VARIABLE_OUTPUT data null; VARIABLE_INPUT data:
  {"pointer": "<id of the VARIABLE_OUTPUT block>"} (a block id as a string).
- RESET_INPUT "reset_input.run" — when the input equals trigger_value, output
  reset_value after a delay. data: {"trigger_value": 0, "reset_value": 1,
  "delay_unit": "min", "delay_amount": 1}

BLOCKS THAT DO NOT EXIST (all have appeared in failed AI files):
EQUAL, EQUALS, GREATERTHAN, LESSTHAN, AND, OR, NOT, WRITE, WRITEOUTUNIT,
WRITE_TO_UNIT, DIGITAL_INPUT, ANALOG_INPUT, INPUT, OUTPUT, SENSOR, READ,
RISING_EDGE, FALLING_EDGE, EDGE, EDGE_DETECT, TOGGLE, FLIPFLOP, TIMER,
COUNTER, CONSTANT, PARAMETER. Their correct translations:
  EQUAL→LIKE · GREATERTHAN→BIGGERTHAN · LESSTHAN→SMALLERTHAN · AND→COMP_AND ·
  OR→COMP_OR · NOT→INVERT · WRITE/WRITEOUTUNIT/DIGITAL_OUTPUT→WRITETOUNIT ·
  DIGITAL_INPUT/ANALOG_INPUT/READ/SENSOR→PARAMV · CONSTANT→CONST ·
  TIMER→DELAY_VARIABLE · COUNTER→PULSE_COUNT · SR latch→LATCH ·
  RISING_EDGE/TOGGLE→ composed, see recipes below.

5. RECIPES (PROVEN SHAPES — REUSE THESE)
--------------------------------------------------------------------------------
R1. THRESHOLD ALARM WITH PERSISTENCE (the workhorse — most requests are this):
    PARAMV(value) → BIGGERTHAN ← CONST(limit)
    → [optional gate: COMP_AND ← CALENDAR/CRITERIA]
    → DELAY_VARIABLE ← CONST(seconds, on put 1)
    → ALARM{pri,...}
    For "below limit" use SMALLERTHAN. Verified live.

R2. TOGGLE ON RISING EDGE (verified live):
    PARAMV(digital signal) → PULSE_COUNT{periode:"day",
      type:"flank_rising_edge", periode_amount:1} ← CONST(1) on put 1
    → MOD ← CONST(2)
    → VIRTUALOUT (or WRITETOUNIT with an explicit confirmed target)
    Caveat: the count resets each period, so 0/1 parity can flip at the
    period boundary; widen the period if that matters.

R3. HYSTERESIS / HOLD UNTIL RESET:
    comparator(high) → LATCH.put0 (set); comparator(low) → LATCH.put1 (reset);
    LATCH output → downstream.
    Formula alternative (one block, production-verified): FORMULA with
    (inp0 >= inp1 ? 1 : (inp0 < inp2 ? 0 : state)) — inp0 value, inp1 high
    limit, inp2 low limit; `state` holds the previous output between limits.

R3b. ENABLE SWITCH (the fleet's most common IF usage — 69% of IF gates):
    CONST(boolean, labelled e.g. "Aktiver styring") → IF.put0; value → IF.put1
    → WRITETOUNIT/VIRTUALOUT. Gives the customer a hand-flippable on/off for
    the whole behaviour. Prefer this over hardcoding always-on writes.

R4. PICK SETPOINT BY CONDITION (night/eco setback, spot price):
    condition (CALENDAR / WEATHER_SUN / SPOT_PRICE_LOW) → SELECTOR.put0;
    CONST(setpoint A) → put1; CONST(setpoint B) → put2; output → VIRTUALOUT
    or (explicitly confirmed) WRITETOUNIT.

R5. COMPUTED KPI / VIRTUAL VALUE:
    PARAMV readings → arithmetic blocks or FORMULA → VIRTUALOUT.

R6. FAN-OUT: one output may feed many inputs (e.g. one comparator triggering
    several alarms). Never wire two sources into one input.

--------------------------------------------------------------------------------
6. WHAT YOU CANNOT KNOW — AND MUST NOT INVENT
--------------------------------------------------------------------------------
- Real driver ids exist only on the actual plant. Use ONLY ids the user
  pasted/confirmed. Otherwise: "data": null and
  "override": {"alias_text": "TODO bind: <what to select>"} — the block
  imports with a red title and the user binds it in the designer dialog.
- Same for calendar ids (CALENDAR) and tag bindings.
- A unit/device address ("000:001", "IWT01") is NOT a parameter. If the user
  gives only a unit, leave the binding as TODO and say which unit to pick from.
- Never guess which hardware parameter a WRITETOUNIT should target.
