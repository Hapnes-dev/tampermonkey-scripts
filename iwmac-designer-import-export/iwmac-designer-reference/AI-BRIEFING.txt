IWMAC DESIGNER PANEL GENERATION - AI BRIEFING
==============================================
The output contract for any AI (Copilot agent, Claude, GPT) that generates
an "iwmac-designer-panel" .json file. The file is inserted into the IWMAC
Designer with the "Insert JSON..." button (IWMAC Designer Import/Export
userscript, Panel JSON section under Manage Files).

ROUTE FIRST. If a user asks for a .json file after discussing an IWMAC
panel, preserve the panel context and generate an iwmac-designer-panel
document. Do not serialize the source data into a custom JSON schema. If a
known-good export is attached, inspect it before generating or modifying the
panel; use it as the panel-type example and preserve its structural
conventions unless a normative contract requires otherwise.
AI-REQUEST-ROUTING.md owns that decision and names the panel type; this file
tells you how to build what it names. Reading this file first and skipping
the routing step is how both failures in ROMKONTROLL-GENERATION-CONTRACT.md
section 13 happened.

WHAT THIS FILE OWNS: the envelope, the 17-field object template, the object
allowlist, the layout rules, the per-panel-type recipes, the linking
procedure and the self-check. It is enough on its own to produce a valid
panel.

0. SOURCE PRECEDENCE (NORMATIVE - APPLIES TO EVERY PANEL TYPE)
--------------------------------------------------------------
When two sources disagree, the higher rank wins. Name the rank you used in
your verification report. This is the same list as
VENTILATION-GEOMETRY-CONTRACT.md's and MASKIN-GENERATION-CONTRACT.md's
front matter and documentation-rules.json -> source_precedence; there is
exactly one list, and it is not restated anywhere else.

  1. A panel JSON or screenshot supplied with the current task.
  2. A real production export of the same panel type and system type
     (reference_data/*.json).
  3. The measured, evidence-tagged geometry contract for the panel type
     in hand: VENTILATION-GEOMETRY-CONTRACT.md for a Ventilasjon panel,
     MASKIN-GENERATION-CONTRACT.md for a Maskin / machine-room panel,
     OVERSIKT-GENERATION-CONTRACT.md for an Oversikt / store-overview /
     case-position / byggeplan panel,
     LIST-PANEL-GENERATION-CONTRACT.md for a spjeldliste or any other
     container-built list panel.
  4. Panel-specific rules in iwmac-designer-reference/CLAUDE.md.
  5. This briefing.
  6. PANEL-TYPE-GUIDE.md.
  7. DESIGN-OBJECT-CATALOG.md.
  8. Generic visual-design advice.

DO NOT AVERAGE CONFLICTING COORDINATES. Use the highest-precedence source.
Two anchors that disagree are two different panels, not one panel measured
twice: splitting the difference produces a layout that matches neither and
that no site will recognise.

Three consequences that catch agents out:

- A SIZE IN THE ALLOWLIST OR THE CATALOGUE IS A TOOLBOX DEFAULT, NOT A
  PLACEMENT. Rank 7 loses to rank 2. Seven objects in the ventilation
  references are placed at a size the catalogue does not list - the sidebar
  header is 60x25 in the palette and 250x20 on every real ventilation
  panel.

- A SUPPLIED JSON OUTRANKS EVERY MEASUREMENT PRINTED IN THIS FILE. Its
  coordinates, sizes, z-indexes, object vocabulary and ordering are the
  template. The numbers in 7a were measured from a different export.

- OBJECT COUNT IS NOT A QUALITY TARGET. Coverage of the required production
  roles is the target (7a-3 lists them). A panel is not better for having
  more objects, and not worse for having fewer - it is wrong when a
  required role is missing or a coordinate was invented.

WHEN THE EVIDENCE DOES NOT EXIST, SAY SO. Do not guess a coordinate to fill
a gap, and never invent an obj_id, driver id, unit id, parameter alias,
file path or navigation target. Report what is missing and what you would
need to measure it. A stated gap is recoverable; an invented number is not,
because nothing downstream marks it as invented.

1. WHAT YOU ARE MAKING
----------------------
A plant-view panel: absolutely positioned objects on a 1400 x 750 canvas.
Objects are either TEXT (headers, labels), VALUE displays (numbers that show a
live reading once linked), STATUS symbols (LEDs, alarm bells, state strips) or
EQUIPMENT icons (fans, pumps, valves, pipes). You lay them out and describe
each signal in alias_text. A HUMAN links each object to a real driver
afterwards inside the designer - you NEVER invent driver ids.

2. THE OUTPUT FILE - EXACT SHAPE (NORMATIVE)
--------------------------------------------
Reply with RAW JSON only. No markdown fences, no comments, no trailing text.

{
  "format": "iwmac-designer-panel",
  "version": 1,
  "generator": "your-agent-name",
  "source_plant_id": "PLANT_ID_OR_EMPTY",
  "panel_name": "PanelName",
  "panel_width": "1400px",
  "panel_height": "750px",
  "counts": { "single_objects": N, "containers": 0, "graphics": 0 },
  "background_embedded": false,
  "panel": {
    "plant_id": "PLANT_ID_OR_EMPTY",
    "panel_name": "PanelName",
    "panel_width": "1400px",
    "panel_height": "750px",
    "org_image_name": "",
    "image_name": "",
    "saved_by": "copilot",
    "single_objects": [ OBJECT, OBJECT, ... ],
    "containers": [],
    "graphics": []
  }
}

counts.single_objects MUST equal the real array length. counts.containers
is 0 and panel.containers stays [] in every panel type EXCEPT list panels
(section 7c), where each table row is a container and counts.containers
MUST equal that array's real length.

BACKGROUND ARTWORK (optional) - three ways, in priority order on insert
(picked file beats image_svg beats image_data). NOT ON VENTILASJON: a
vent panel is drawn with designer objects on the blank background, never
with artwork - see section 7a, "VENTILATION UNIT".

1. YOU CAN DRAW IT YOURSELF (v1.2.0+): put raw SVG markup in the panel
   object as "image_svg". Rules: the string starts with <svg, carries
   viewBox="0 0 1400 750" (match the panel size), NO <script> tags, and
   its coordinates line up with your object positions (same pixel space).
   Insert validates it, converts it to a data-URL and embeds it as the
   background - so one file delivers artwork AND objects.
   What to draw (keep it schematic, like the production PNGs):
   - a page background in the colour the user asked for, or the colour
     of the production reference you were given (most production PNGs
     are light, around #eef1f4), and a tinted side/section zone
   - a rounded-rect machine/plant enclosure with a small title text
   - the pipe, duct or tank runs that the panel's value boxes annotate,
     as thin flat bands behind them, plus flow arrows
   - dashed zone boxes around a subsystem
   Background colour is the user's call, or the chosen production
   reference's - preserve a supplied background unless a change is
   asked for. Never draw values or symbols the OBJECTS already
   provide (no fake numbers, LEDs or fans in the SVG). NEVER for a
   Ventilasjon panel: its ducts, dampers, coils and fans are OBJECTS
   (section 7a), so drawing them here yields a doubled, un-linkable
   panel that no technician can maintain.
2. If the user supplies ready image data, put it in "image_data" as a
   data:image/png;base64,... string with "converted": "true".
3. If they only have a file on disk, leave the fields out - the Insert
   dialog's background picker (v1.1.0+) embeds it for them.
Set the envelope's "background_embedded": true when 1 or 2 is used.

MASKIN (MACHINE PICTURE) - ROUTING FIRST. Everything measured about a
Maskin panel - canvas, background ownership, the z-index bands, the
eleven obj_ids, the eight named role clusters with their coordinates,
the compressor pitch, the MT-to-LT translations, the anomalies, the
sanitization contract and the four request classes - lives in
MASKIN-GENERATION-CONTRACT.md, WHICH IS AUTHORITATIVE ON CONFLICT. The
procedure is MASKIN-AUTHORING-GUIDE.md, the acceptance tests are
MASKIN-QA-CHECKLIST.md, the promptable digest is
MASKIN-COPILOT-PREFLIGHT.md, and the committed 66-object production
fixture to copy is reference_data/maskin-10229-sanitized.json. Validate
with: python validate-maskin-panel.py PANEL.json --profile TEMPLATE-10229
Two Maskin facts that belong here because they are envelope-level and
catch agents out on every panel type:
- The z-index list in section 5 of this file and in CLAUDE.md is
  VENTILATION-scoped. Maskin uses different bands (110 / 360 / 375 /
  1000 / 1100, contract section 3). Applying the ventilation bands to a
  Maskin puts every value pill underneath the artwork.
- A production export never emits the literal string "driver_id". Its
  unlinked objects carry an EMPTY driver_id, and the host then sets
  linked "true" anyway (CLAUDE.md section 5). A generated demo MUST emit
  the literal placeholder. That asymmetry is how you tell the two modes
  apart, and the validator keys on it.

MASKIN ARTWORK - when asked to draw or modify a machine-picture
background, follow maskin-drawing-method.txt (knowledge file; companion
image maskin-light-style-reference.png) exactly:
- Layout doctrine: MT compressor group upper-left, LT group lower-left,
  oil separator on the discharge riser top-left, gas cooler (white box
  with fan circles) top-right, heat-recovery HX branch top-center,
  receiver (vertical vessel, coil + level bar) right-of-center, suction
  headers exit bottom-right as labeled line ends (Liq. consumer, M-T
  Suct., L-T2 Suct., L-T Suct.), grey info/status panel far right.
- Circuit colour = function, one per circuit: orange = high pressure /
  discharge, yellow = receiver/liquid, cyan = MT suction, blue = LT
  suction. Orthogonal pipes only, small flow arrows.
- One symbol family reused: compressors (MT1..n/LT1..n), fan circles,
  one valve style with its V-xxx tag adjacent, WHITE pills drawn EMPTY
  (number objects render into them), darker grey pills = setpoints.
- BACKGROUND COLOUR: preserve the background of a supplied production
  export unless the user explicitly asks for a change; for new artwork
  take the colour from the user's requirement or from the production
  reference chosen for the job. The kit ships one rendered reference,
  maskin-light-style-reference.png (1:1 from the Illustrator source
  maskin-light-template.ai; its real layers are Backround / Ror /
  Maskinrom), and it is a light template - that describes the file that
  happens to be committed, not a required skin. Everything else in this
  block applies at any background colour.
- Vrec is the receiver FLASH-GAS valve: draw it on the cyan
  suction-side line, never on the yellow liquid line.
- NEGATIVE example, corrected 2026-08-10: generated-maskin-example.json
  was listed here as a worked example. It is not one. It is an authored
  image_svg demo, and measured against the production export it drops
  three roles (the entire third LT compressor), invents one, substitutes
  two purpose-built obj_ids with generic value pills, emits
  zIndex "default" on all 63 objects, and places 0 of the 62 shared
  roles at the production coordinates. It insert-verifies 63/63 and is
  still wrong - which is the lesson. The audit is
  MASKIN-GENERATION-CONTRACT.md section 13. Copy
  reference_data/maskin-10229-sanitized.json instead.

Editing an existing Maskin compressor bank from an exported panel JSON
The full procedure, the four request classes and the failure catalogue
are MASKIN-AUTHORING-GUIDE.md; the measured cluster geometry and the
compressor pitch are MASKIN-GENERATION-CONTRACT.md sections 5-6. The
five rules that are envelope-level:
- Decide the deliverable BEFORE editing. A background-only patch changes
  image_data and has zero counts plus empty single_objects, containers and
  graphics. An entire/full JSON preserves the complete source document and
  every existing object; only requested additions may be appended. Insert JSON
  APPENDS, so insert a full export only on an empty canvas unless duplicates
  are intentional.
- Inspect the source target column before adding objects. Artwork alone does
  not require parameter objects. Preserve every existing object unless the
  request explicitly authorizes a change. If boxes are requested, clone the
  nearest role match atomically: a fixed-speed C4 matching C3 gets status,
  capacity and runtime only, never C1's extra VSD row. New objects use id and
  driver_id "driver_id", linked "false", blank link/unit fields and clear
  alias_text; NEVER invent a driver ID.
- ARTWORK FIRST, OBJECTS SECOND. Never add a dynamic object before the artwork
  drawing its anchor exists - a status strip with no compressor under it and a
  value pill on white are both well-formed to every JSON check that will run.
  And an unknown plant parameter is NEVER a reason for alias_text "": the alias
  is the relink key, so an object without one can never be linked by anyone.
  Give it the role's alias (grammar "C<n> <MT|LT> <role>"), ship it unlinked,
  and REPORT the gap. maskin-akpc-link-map.json carries C1-C3 only; a fourth
  compressor's parameters are unresolved until that plant's dump is supplied.
- Treat the compressor column as one template and apply one measured vector to
  its compressor art, upper/lower branches, static label, empty pills and
  requested object coordinates. Reuse a pitch measured from a NAMED pair and
  say which pair - the production pitch is 79 to 82 px, and averaging it into
  a constant is forbidden. Background owns pipes, equipment, labels,
  status/pill artwork and empty fields; dynamic objects own live state/values.
- Copy each source pixel's alpha VERBATIM; NEVER MULTIPLY it and never paste an
  opaque rectangular crop. A mask is BINARY - a pixel is copied or it is not. A
  soft, feathered, blurred or opacity-scaled mask multiplies the source alpha,
  and then the compressor, its pipes, its labels and its pills all come out
  faded TOGETHER; that uniformity is the tell. Sample every source's
  centerline, colour, alpha, thickness, anti-aliasing and junction geometry
  exactly, and reproduce EVERY row it has - a line that looks 2 px wide is
  often 3 rows, the outer ones partially transparent, and dropping them makes
  the copy thinner and harder-edged than the original. Measure each header
  SEPARATELY: on one panel the discharge and suction headers legitimately
  differ in thickness. The fixture's orange 191/255/64 three-row header, opaque
  two-row cyan header and opaque two-column branches are example-specific
  measurements, not universal defaults.
- Reparse full JSON; check counts, sequential names, the exact object diff and
  protected existing fields. Render full panel, zoomed bank and background plus
  dynamic overlay; a background-only preview cannot prove overlay alignment.
  Compare by role key (obj_id + alias_text + tag_text), NEVER by array index.
  Restart from the original export after any failed iteration.
Extending an existing bank is nine ORDERED steps - six of the seven documented
failures were order failures, not drawing failures: MASKIN-AUTHORING-GUIDE.md
section 4a (rules M-A01..M-A09). Acceptance: MASKIN-QA-CHECKLIST.md stage C0,
the background alone, at native size. Drawing doctrine and the pixel rules
R1-R5: reference_data/maskin-drawing-method.txt. On ANY visual failure restart
from the retained original source, never from the damaged derivative.
Regression fixture/test: tests/fixtures/maskin-compressor-bank/ and
tests/test_maskin_compressor_bank.py plus tests/test_maskin_10229_contract.py

READING THE EXISTING DRAWING: "image_svg_trace" (v1.5.0). Exported panel
jsons MAY carry panel.image_svg_trace - an automatic VECTOR TRACE of the
panel's current raster background (or the SVG itself when the background
was SVG). It is INPUT FOR YOU, never output:
- READ it to learn how the drawing is structured: the path coordinates
  tell you where the pipe runs, vessels, frames, side panels and section
  boxes sit - the geometry the plain PNG cannot tell you. Since v1.5.1
  the path fills are the drawing's REAL colours (palette derived from the
  image), and colour is meaning in these schematics: orange = hot
  gas / discharge, blue/cyan = suction, yellow = liquid, green = OK /
  running, red = alarm. Use the fill colours to tell the circuits apart.
- USE that structure when asked to generate or modify artwork: author
  your OWN clean image_svg whose layout matches the traced geometry
  (same runs, same enclosure positions), drawn with crisp shapes.
- NEVER copy image_svg_trace into image_svg or echo it back: traced art
  has thousands of ragged paths and text as outline blobs - it is a map,
  not a drawing. Insert ignores/strips the field; the embedded image_data
  always remains the real background.
- NEVER read label text out of the trace: traced digits are chipped
  outlines and misread silently (3 vs 2, 8 vs 6, F vs P, I vs 1 - proved
  on a real store plan). Take names/numbers from the objects' tag_text /
  alias_text, or view the image_data png; the trace supplies geometry
  and colours only.

5. LAYOUT RULES
---------------
- Canvas 1400 x 750. Keep everything inside x 20..1380, y 10..730.
  EXCEPTION: list panels (section 7c) overflow on purpose - the real
  production spjeldliste runs rows to y 4646 and content to x 1585 on a
  nominal 1400x750 panel; the plant view scrolls. Only list panels may
  do this.
- PANEL-TYPE GEOMETRY WINS. The column grammar in this section is for
  TABLE-STYLE panels (mode A: rack overviews, energy lists, status
  pages on an empty canvas). Where a panel type has its own measured
  layout - Ventilasjon (7a), spjeldliste (7c), hotel Oversikt (7d) -
  that layout overrides every bullet below it. Do not apply the column
  grammar to a schematic panel.
- Table-style: organize in section columns roughly 300 px wide
  (x = 20, 320, 640, 960).
- Table-style: each section has a header bar (number_v3_header_grey75,
  W 250-280; the Ventilasjon sidebar uses exactly 250x20) then rows
  every 28-30 px starting ~35 px below the header.
- A value row = label at column x+5 (W 100-150) + value at x+150..180.
- Never overlap objects. Leave 8+ px gaps. Overlap is measured on
  RENDERED extents, not on posWidth: a left-aligned label whose text is
  narrower than its box does not overlap its neighbour.
  EXCEPTIONS - four classes, all intentional, none of them a defect to
  "fix" (7a-5 is what the z-index bands are for):
  1. a value box sitting on the duct or pipe it belongs to;
  2. a con_* connector edge landing ON its duct - a stub that stops
     short is the defect;
  3. a damper symbol laid over a continuous duct column - NEVER shorten
     the duct to clear it;
  4. an equipment body straddling the run it conditions.
  Anything outside that list is a real overlap. See
  VENTILATION-GEOMETRY-CONTRACT.md for the measured exception table.
- TEXT IS NEVER COVERED. None of the four classes puts a live object on
  DESCRIPTIVE TEXT: an alarm bell, status symbol, value or navigation
  element never overlaps a nonblank label, at any z-index, unless the
  supplied production panel proves that exact overlap. Text, icons and
  values each get their OWN rectangle - a table or list row reserves a
  static label cell, a blank icon cell and a blank value cell. Never
  append an icon at the end of a text string without a reserved cell,
  and never treat the space right of a label as free because today's
  text is short. Executable check: validate-visual-correctness.py
  (VC-T*); the rule's owner is VISUAL-CORRECTNESS-CONTRACT.md (GLOBAL).
- SIZE VALUES FOR EVERY ALLOWED STATE, NOT THE CURRENT ONE. When the
  source provides allowed display values - format_extra enum maps, an
  "Allowed values" workbook column, state definitions, translated
  labels - parse ALL of them before choosing the value-object width.
  "0 = Alarm / 1 = OK / 2 = Communication error" needs a box for
  "Communication error" (19 chars, ~139 px at the 13 px font) even
  while the current reading is "OK"; a 42 px numeric pill truncates
  it. Numeric ranges ("-200.0 to 200.0") size for the widest bound
  with sign and decimals, plus the unit when it shares the object.
  Executable check: validate-visual-correctness.py --allowed-values
  (VC-W*); owner VISUAL-CORRECTNESS-CONTRACT.md section 5.
- Table-style: title number_v3_label_12px_bold at top-left; alarm bell
  top-right (~x 1240). A schematic panel has neither - never add a
  title bar or a corner bell to a Ventilasjon panel.
- TEXT ENCODING: emit UTF-8. The Insert JSON flow reads files as UTF-8,
  production panels carry Norwegian letters, degree signs and
  m3-superscripts, and rendered tests confirm they survive the real
  pipeline. Write "°C", never "gr C"; write "høyfart", never
  "hoyfart". The catalogue itself uses "RT401 °C".
  The mojibake risk lives in other channels (pasting through a terminal,
  an ISO-8859-1 page, old mail) - that is a transport problem to fix at
  the transport, not a reason to degrade the panel text.
- SECTION 5 IS THE TABLE-STYLE DEFAULT. Sections 7a (ventilation), 7c
  (list panels) and 7d (hotels) override it IN FULL - not rule by rule.
  When you are on one of those panel types, section 5's columns, row
  pitch, title position and alarm-bell position do not apply at all. Say
  which section you are working under before you place anything.

6. WHAT THE FIELDS MEAN (SO YOU FILL THEM RIGHT)
------------------------------------------------
- tag_text: the visible text of headers/labels, and the small caption on
  "tag_up"/"con_" boxes. Ignored by value_only, LEDs, bells, state strips.
- alias_text: the SIGNAL DESCRIPTION shown to the human who links the object
  (e.g. "Pc discharge pressure", "MT compressor 2 run status"). Set it on
  every value/status/equipment object. Take the names from the source
  document (P and ID sensor names like Po, Pc, Prec, Sgc, Sd, Ss, Shr2).
- containers: empty array EXCEPT in list panels (section 7c), where every
  table row is one objects_container. graphics: always empty.
- No background image: background_embedded false, org_image_name "".

7a-8 TAG CONVENTION. tag_text = instrument code + unit ("RT401 °C",
"RF401 m3/h", "KA401 %", "QD401 Pa"); alias_text = the sentence a human
reads. Codes follow the vent controller: RT=temp, RF=flow,
RH=humidity, KA=damper, LR=motor/output, LX=rotor, QD=filter pressure,
JV=fan, JP=pump, LV=coil/valve, SB=power, RP=CO2, RY=smoke.

Write the real degree symbol: "RT401 °C". Never "gr C". The Insert flow
reads UTF-8, production exports carry 13 degree-signed tags, the object
catalogue itself prints "RT401 °C", and rendered tests confirm they
survive. Mojibake comes from other transports (pasting through a
terminal, an ISO-8859-1 page) - fix the transport, do not degrade the
panel text. The same holds for "m3" written as m3 with a superscript
three, "høyfart" and every Norwegian letter.

ONE OWNER PER PIECE OF TEXT. Do not add a standalone label when the
equipment object already shows its tag; do not add a caption when the
value object renders tag_text. Two objects printing the same words is a
defect, not redundancy - the repeat offenders are KA502, Cool, Rotor,
VGV and Kurver. Emit one of those captions only when the production
export you selected actually contains it.

ONE POSITION VALUE PER DAMPER, ONE ALARM PER GUARDED ROLE. A second
KA501 or KA401 box left over from an earlier revision is a defect even
when both render legibly. Alarm uniqueness is keyed on (signal,
component): two dampers on one unit legitimately carry two "Malf.
damper" alarms - E3 has exactly that, 243 px apart - but two alarms on
ONE component do not.

7a-9 HOW A VENT PANEL IS JUDGED. Every line here is testable; the test
is in VENTILATION-QA-CHECKLIST.md and, where a rule id is given, in
validate-ventilation-panel.py.

STRUCTURAL (Stage A) - the JSON is malformed or the vocabulary is wrong
 - an obj_id that is not in the catalogue (renders as a broken box)
 - counts that do not equal the array lengths                   V-S01
 - object names not sequential object_0..object_N        V-S03, V-S04
 - non-integer or out-of-canvas coordinates                     V-S05
 - zIndex mixing explicit bands with "default"                  V-S06
 - a panel.image_svg on a Ventilasjon panel                     V-S07
 - a missing or replaced background                             V-S07
 - "gr C" where the panel should print °C                       V-S09

GEOMETRIC (Stage B) - the drawing does not read as ductwork
 - a duct run broken into segments that do not meet
 - a connector that stops short of the target it should land on V-G03
 - a vertical crossover that does not reach both horizontal runs
 - a damper cleared by SHORTENING the duct instead of overlaying it
 - a cluster split: equipment moved without its value, output,
   alarm, pump or valve                                         V-P01
 - a fan pointing against its run's airflow direction
 - two position values on one damper                            V-G07
 - two alarms guarding one component                     V-G05, V-P06
 - an inlet damper from a different template's family

VISUAL (Stage C) - it parses and it renders, and it is still wrong
 - a value box overlapping a tag, another value, or a control
 - an alarm bell on top of the component instead of beside it
 - an LED outside its body, or covering the tag or the value    V-P05
 - a duplicate free-standing caption                            V-G04
 - a duplicated or coincident sidebar row                       V-G06
 - a heading that is off-centre because widths were equalised   V-P08
 - a hover tooltip captured in the QA screenshot and mistaken for
   panel content

LINKING (Stage D)
 - a source plant's driver_id, unit_id or link_tag carried into a
   demo                                                         V-S08
 - an invented driver id, unit id, file path or panel target
 - alias_text stripped during sanitization (it is what a human links
   by afterwards)

NOT A DEFECT, and not to be "fixed":
 - a value box sitting on the duct it belongs to
 - a con_* connector edge landing ON its target
 - a damper symbol overlaying a continuous duct column
 - an equipment body straddling the run it conditions
 - an object count lower or higher than the reference, when every
   required role is present and no coordinate was invented
 - the same output code on two different components with different
   alias_text (E4 carries SB520 % on both the cooling coil and the
   electric heater - production, deliberate)
 - a room-endpoint value object whose tag_text is a single space, its
   caption supplied by a separate label object

7b. HOW PANELS ARE DRAWN TODAY (PRODUCTION CONVENTIONS)
-------------------------------------------------------
Mined from 194 real compiled panels on 59 plants (reference_data/
panel-conventions.json). Follow these so your output matches house style.

Panel inventory per plant (use these names): Oversikt (store floor plan),
Maskin (machine room / rack), Energi (energy meters, small panel),
Ventilasjon 360.NNN (one per ventilation system, keep the system number),
VGV (heat recovery), Waterloop, Kondenssystem. Also seen: Varmesentral /
Varmeanlegg 320.NNN (heating), Torrkjoler, Isvannsystem, Gatevarme,
Tappevann, Kurver, Fordampere Frys/Kjol, and multi-part overviews
(Oversikt del 1 / del 2, Oversikt Plan 1A/1B/2) on big sites. Swedish
stores use Oversikt Butik / Larmoversikt, Danish use Overblik Butik.

Size: three standards in production - 1400 x 750 and 1400 x 755 on newer
plants (755 is the designer's own preset), 1280 x 1024 on the older fleet.
ALWAYS match the plant's existing panels; default to 1400 x 750 for new work.

Containers appear on only 3 of 194 panels and graphics on 0 of 194 - your
output keeping containers/graphics empty IS the house style. The exception
is the LIST PANEL (spjeldliste, section 7c), which is container-built by
design. Older plants
contain legacy V2 object ids (alarm_anim.gif, number6, red_led_small,
sub_page_1); they still render but are NOT modern style - never emit them.

OVERSIKT OWNER: OVERSIKT-GENERATION-CONTRACT.md. That file is the normative
source for any Oversikt, store-overview, case-position or byggeplan panel -
the input routing decision tree, the preserve-and-patch rule, the controller
identity and coverage contract, the placement rule, background and link
preservation, the sanitization rules, and the verification report. Read it
before generating or repairing one. OVERSIKT-AUTHORING-GUIDE.md is the
step-by-step procedure, OVERSIKT-QA-CHECKLIST.md the acceptance tests, and
validate-oversikt-panel.py the same rules as code. The normative reference
export is reference_data/oversikt-10113-sanitized.json (72 objects, 21
controller clusters, real store-plan background). The modes below are the
summary and the standalone fallback.

THE RULE THAT OUTRANKS EVERY MODE BELOW: if the user supplies a production
panel JSON, that document is the geometric and object-coverage template.
PRESERVE AND PATCH, NEVER REBUILD. A PDF, a byggeplan drawing or a
screenshot may identify equipment and room names, but it may NEVER silently
override or reduce a supplied production export - a store-layout drawing
routinely omits instrumented positions, so fewer positions in the drawing
than in the JSON means the DRAWING is incomplete. Report the discrepancy and
keep the clusters. An Oversikt is a MAP, not a dashboard: regrouping its
objects into cards, rows or a legend destroys the only thing the panel type
exists to show, even when every object and every binding is correct.

Backgrounds: every FINISHED production panel sits on a custom PNG (floor
plan or schematic) with objects placed on top. You cannot generate that PNG,
so you have two modes:
  MODE A - BLANK PANEL (default): table-style sections on the empty canvas,
  like generated-panel-example.json. Immediately usable.
  (If the user pastes a data:image/... string, embed it per section 2 and
  you get MODE A with real artwork in one file.)
  MODE B - CLUSTER KIT (when the user says the panel will get a background
  image, or gives a list of cooling positions): emit one CASE CLUSTER per
  position, laid out in a tidy grid (90 px column pitch, 90 px row pitch,
  starting x 40 y 60), each cluster labeled via alias_text with its position
  name. The human inserts your file, then drags each cluster onto the floor
  plan. Do not try to guess floor-plan coordinates.
  A KIT IS A HAND-OFF, NEVER A FINISHED OVERSIKT. The 90 px grid is scoped
  to this mode alone; it is not an Oversikt layout. Say in the delivery text
  that the file is a cluster kit awaiting placement. A panel delivered as
  finished with its clusters still in a grid is a defect (contract OV-C2).
  MODE D - BYGGEPLAN UPLOAD (when the user uploads a store floor-plan
  drawing - a byggeplan PDF/image showing walls, rooms and the
  refrigeration fixtures, AND NO PRODUCTION EXPORT OF THE PANEL EXISTS):
  you DO have coordinates, so deliver a complete Oversikt in one file.
  If a production export IS supplied, this mode does not apply: patch that
  export instead, using the drawing only to prove a specific difference,
  and name each patch individually.
  1. READ the plan. Room names come from its text labels (Kjolerom,
     Fryserom, Olrom, Lager, Kontor, Spiserom...); refrigeration
     fixtures are the labeled cabinet boxes (e.g. "Fryseskap ... Dorer"
     vendor blocks) and the cold/freezer room outlines. Shelving
     gondolas and dimension lines are NOT cooling positions - skip
     them. If the number of cooling positions is unclear, LIST what you
     found and ask before generating.
  2. DRAW a simplified floor plan as image_svg (section 2 rules,
     viewBox 0 0 1400 750): scale the whole plan to fit, keep the
     aspect ratio, light background, thin grey walls, room outlines
     with small room-name texts, subtle tinted zones for cold/freezer
     rooms. No fixtures, no values, no symbols - the objects provide
     those. Keep it as plain as the production store-plan PNGs.
  3. PLACE one CASE CLUSTER per cooling position AT its location in
     YOUR svg's pixel space - clusters sit ON the room/cabinet they
     monitor, alias_text named from the plan's room/cabinet labels.
     Cluster shape follows the CASE CLUSTER block below, and a plan
     cannot prove which relays a controller exposes: from a drawing
     alone, emit the shape you can justify and say so. Never force four
     objects per controller to make the panel look complete.
  3b. LABEL THE RESULT A DRAFT. From a drawing alone you have no plant
     id, no controller addresses and no parameter aliases, so every
     binding is empty, the coordinates are estimated at a scale you
     must state as a number, and the delivery text says "draft". A
     stated gap is a valid deliverable; a guessed binding is not.
  4. Add the standard trim: panel title top-left, alarm bell top-right.
  The result inserts as a finished-looking Oversikt; the human then
  links each cluster and may later replace the background with the
  drawn PNG artwork.

THE CASE CLUSTER (the standard Oversikt pattern, one per disk/rom; every
member links to the SAME case controller). Two measurements, two scopes -
NEVER AVERAGE THEM, and never average either with a supplied export.

  Scope FLEET-194 (this survey: 28 occurrences mined across 16 stores, plus
  a 3-member variant without the cooling symbol, common on freezer rooms).
  Offsets from the cluster's top-left:
    V3_R_34px_circular_alarm_nrm   at dx 12, dy 0    (alarm bell)
    number_v3_40px_no_conn_no_tag  at dx 7,  dy 22   (air temperature)
    V3_R_28px_circular_cooling_nrm at dx 10, dy 35   (cooling relay)
    V3_R_28px_circular_defrost_nrm at dx 28, dy 38   (defrost relay)
  Footprint ~62 x 66 px.

  Scope TEMPLATE-10113 (measured object by object from the committed
  reference export, oversikt-10113-sanitized.json - 21 clusters):
    V3_R_34px_circular_alarm_nrm   at dx 4, dy 0
    number_v3_40px_no_conn_no_tag  at dx 0, dy 35
    V3_R_28px_circular_cooling_nrm at dx 7, dy 58
    V3_R_28px_circular_defrost_nrm at dx 7, dy 58   (deliberately
      coincident with the cooling symbol - the host draws whichever state
      is active; this is not an overlap defect)
  Footprint 42 x 86 on 15 clusters, 42 x 57 on the alarm-plus-value ones.

COVERAGE IS DERIVED, NEVER FORCED TO FOUR. On the reference panel 15
clusters carry all four roles and 6 carry alarm plus value only, because
those controllers expose no cooling or defrost relay. Adding a cooling or
defrost symbol to a two-member cluster INVENTS A BINDING. Object counts and
cluster counts are evidence, not targets: a store has as many clusters as it
has cooling positions, and a candidate is judged against ITS OWN source.

CLUSTERS ARE ATOMIC AND SPATIAL. Place every member or none, move a cluster
with ONE vector applied to every member, and center or anchor each cluster
on the case, cabinet or room it monitors in the background artwork. A
cluster on empty floor, in a margin or in a grid is a defect even when its
bindings are perfect. That is LEVEL 1, and it is necessary, not sufficient.

LEVEL 2 - THE TEMPERATURE BUBBLE GOES IN THE CENTER OF THE BOX (contract
7.1a/7.1b, rule O-G08). The value object itself - the
number_v3_40px_no_conn_no_tag - must be centered on the EQUIPMENT FOOTPRINT:
the rectangle of the physical refrigeration box, cabinet, display case or
room drawn in the artwork. Seven terms, never interchangeable: equipment
footprint (that rectangle), equipment center (its center point), value
anchor (where the bubble's top-left goes), cluster geometry (the member
offsets above), text-label anchor (the caption - NOT the box), shared
footprint (a combined A/B case under one regulator, the union, and only
where evidence shows it), and an unmeasurable target (report the gap).

  value_left = round_half_up(x + (width  - w) / 2)
  value_top  = round_half_up(y + (height - h) / 2)

(w, h) is THIS panel's value-object size - never silently force 42 x 22.
Measured on the image and placed on the canvas, state and apply
scale_x = panel_width / image_width and scale_y = panel_height / image_height
first. Never center on the equipment's text label, the regulator name, the
cluster bounding box, an approximate or OCR coordinate, or empty floor, and
never infer a box from a nearby caption. Alarm, cooling and defrost do NOT
need the center - they hang off the value object. If the footprint cannot be
established, report the evidence gap and emit no coordinate for that
controller. A supplied production export still outranks this rule: report an
off-center production position, do not "correct" it unless the user asks or
higher-ranked evidence proves it wrong.

A PANEL JSON CONTAINS NO EQUIPMENT-BOX BOUNDARIES, so no script can prove
centering from the panel alone. Measure the footprints into a sidecar
(build-oversikt-footprints.py emits the template; fill it in from the
artwork) and check with validate-oversikt-panel.py --footprints
FOOTPRINTS.json; render with --footprints to draw the measured boxes. Without
that sidecar the honest report is "centering was not verified", not "0
errors". Record per controller: unit_id, source, source_image_size,
panel_size, footprint {left, top, width, height}, value_object_size,
expected_value_position and an evidence_note.

PATCH SCOPE. When the correction is "center the bubbles", the ONLY permitted
object-level differences are posLeft and posTop on temperature/value objects,
and NO field difference at all on any other object. Prove it:
validate-oversikt-panel.py --compare SOURCE.json CANDIDATE.json --patch-scope
value-position. Anything else - a resized bubble, a rewritten alias, a
re-bound driver id, a nudged alarm, a changed zIndex, a reordered array -
fails QA unless disclosed and justified separately.

Z-INDEX (Oversikt scope; these are NOT the Maskin or ventilation bands):
the value box at 110, all three circular symbols at 375, as strings.

alias_text pattern: "Disk 1 Melk alarm", "Disk 1 Melk lufttemp",
"Disk 1 Melk kjoling", "Disk 1 Melk avriming".

Other production habits: Maskin panels are dominated by bare
number_v3_value_only readings placed over the schematic plus V3_akpc state
strips and an V3_ok_alarm_nrm banner. Energi panels are small (under 12
objects), built from json_obj boxes. Ventilasjon panels are drawn
object-only on the blank template: duct pieces (exhaust/inlet/supply pipes),
fans, filters, and number_v3_R_45px_con_* boxes whose connector lines point
at the duct. Condenser/gas-cooler fans often appear as two fans stacked
vertically 27 px apart.

8b. LINKING (WHEN GIVEN THE PLANT PARAMETER SOURCE)
----------------------------------------------------
Normally the human links objects by hand after insert. But if the user
attaches a plant parameter workbook, CSV, JSON or iw_gen_driver_parameters
.sql dump and asks you to link, relink, validate links or diagnose failed
values, the parameter source is MANDATORY binding evidence for every row it
covers. A supplied panel JSON remains rank 1 for geometry, object coverage,
ordering and background. Its EXISTING BINDINGS ARE NOT rank-1 proof merely
because they are present or because the task says "link out".

LINKED STATE IS NOT BINDING VALIDITY. These terms are normative and are not
interchangeable:

- STRUCTURALLY LINKED: linked is "true" and driver_id is non-empty; unit_id
  may be present. This proves only that the document carries binding-looking
  fields. The host sets linked from a literal-string test and never resolves
  the driver against the plant.
- SOURCE-RESOLVED: driver_id resolves EXACTLY and uniquely in the supplied
  plant-specific parameter source, and the resolved row's unit_id equals the
  object's unit_id. The resolved alias/description is recorded beside both
  original values.
- SEMANTICALLY VERIFIED: source-resolved, and controller identity, exact
  alias/parameter meaning, object role, access and datatype where supplied
  all agree. This is the binding appropriate to what the visual object
  represents.
- UNRESOLVED: any intended link that lacks exact and semantic proof. It may
  still be structurally linked and look plausible.
- FULLY LINKED and LINKED-READY may be used only when EVERY intended link is
  semantically verified. PRODUCTION-READY additionally requires every
  panel-type geometry, visual, import and operational QA gate; binding
  verification alone never proves it.

THE INVARIANT. A binding is verified only when its driver_id is copied
verbatim from, or resolves exactly and uniquely in, the plant-specific
parameter source and the resolved unit/controller identity and parameter
meaning agree with the object's intended role. linked "true", a non-empty
driver_id, a familiar suffix, a matching plant prefix or a syntactically
valid identifier is NEVER sufficient evidence by itself.

TASK SCOPE. A layout-only correction preserves binding fields exactly. A
link, relink, link-validation or failed-value task puts those fields IN
SCOPE: check them against the parameter source. "Preserve and patch" means
preserve geometry and document structure; it never means preserve a binding
already shown to be unverified.

THE DUMP: one row per parameter. Columns that matter:
- driver_id: the FULL parameter string (e.g. NNNNN_OJEXHAUST_OJ_1_1_0_4_19).
  This exact string goes into the panel object's driver_id. COPY IT
  VERBATIM - never construct or edit one (the digit groups differ per
  driver type; on the OJ vent driver _4_ = Analog values and _2_ =
  Digital IO, but AKC/EM drivers use other group digits).
- unit_id + unit_name: the unit ("V01" / "360.001 Ventilasjon"). Match
  unit_name against the panel's system number to pick the right unit.
- alias_text: the parameter description ("Actual supply temperature...",
  "Supply motor ON/OFF") - your matching target.
- application: "Analog values" (readings/setpoints) vs "Digital IO"
  (status, alarms) - value boxes need analog rows, LEDs/bells/state
  objects digital rows.
- att: r = read-only, rw = writable (setpoint boxes want rw rows).
- eng_unit (degC, %, Pa, m3/h) and format_extra (enum value map).

DETERMINISTIC PROCEDURE, per intended link:
1. Look up the PANEL driver_id exactly in the supplied source. No match is
   unresolved. More than one source row is ambiguous and unresolved.
2. Verify the resolved unit_id exactly. Then verify controller identity.
3. Compare panel alias_text with the resolved alias or parameter
   description EXACTLY. If only capitalization, punctuation, whitespace,
   abbreviation or encoding differs, record BOTH strings and classify the
   difference separately; never call it exact and never normalize the panel
   value before using it as evidence.
4. Verify parameter meaning against the object's role. Verify datatype and
   access where the source supplies them: display values are readings,
   alarm/cooling/defrost symbols are the matching states, and writable
   setpoint objects require a suitable writable row.
5. Record SEMANTICALLY VERIFIED only when steps 1-4 all agree. Fuzzy search
   may list candidates only; it can never authorize one. A candidate becomes
   usable only through one unique source row plus compatible identity and
   role.
6. For a new or repaired binding, copy that row's driver_id and unit_id
   VERBATIM and use its exact alias/description as required by the panel
   contract. Touch no geometry or object identity.

NEVER construct or transform a driver_id. Never edit a plant prefix,
controller number, group digit or suffix. Never convert AK2 to AK3,
001 to 000 or any similar pattern by inference. Never approve by suffix
similarity. A source mismatch stays unresolved unless a higher-ranked
authoritative parameter source proves the exact row.

BINDING VERIFICATION MATRIX. Before any completed-linking claim, build one
row per intended object with these columns:

  object identity | object role | obj_id | controller identity |
  panel driver_id | parameter-source driver_id | driver_id exact match |
  panel unit_id | resolved unit_id | unit_id exact match |
  panel alias_text | resolved alias or parameter description |
  alias match status | access | datatype | verification state |
  reason if unresolved | evidence source

For Oversikt, group by controller cluster and role (alarm, value, cooling,
defrost), NEVER by array index or spatial proximity. Object names such as
object_10000 are preserved as source identity; they are not renumbered to
make comparison easier.

HARD STOP. If any intended link is not source-resolved and semantically
verified, do not call the panel finished, fully linked, linked-ready,
production-ready or verified. Deliver instead: the verified subset; the
matrix; source coverage (verified and unresolved counts separately); exact
unresolved objects/controllers/roles; and the evidence required to finish.
Do not silently change unresolved bindings.

PARTIAL-FILE POLICY. On an existing production export, retain every
unresolved object's original binding fields byte-for-byte and label them
UNVERIFIED in the external report. The panel schema has no verification
field, so never invent one inside the JSON. This retained field is not
approved and the file is not safe to describe as completed. Converting
objects to an unlinked template is a separate, explicit user request with a
panel-type-specific host contract; never do it as an automatic fallback.

Dummies never link: pipes, connectors, arrows, labels, headers, stripes,
banner and spjeldliste text cells. Host literals are not semantic evidence:
id stays "driver_id"; link_name stays the host's established value for the
object; linked, link_tag and unit_ref are transport/state metadata. Never put
a destination panel into link_name; navigation targets use their own
object-specific host contract.

Run parameter-aware Oversikt validation when applicable:

  python validate-oversikt-panel.py PANEL.json --parameters PARAMETERS.xlsx

Use --json-report for the complete matrix. O-S09 checks structural field
consistency only. O-B00..O-B08 own source and semantic binding evidence.

EXISTING OVERSIKT REPAIR. Requests such as "link these objects", "link out
these disks", "I placed them where they should be", "use this updated JSON"
or "match the screenshot to the parameter Excel" route to
