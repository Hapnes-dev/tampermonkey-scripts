IWMAC DESIGNER PANEL GENERATION - AI BRIEFING
==============================================
Self-contained contract for any AI (Copilot agent, Claude, GPT) that generates
an "iwmac-designer-panel" .json file. The file is inserted into the IWMAC
Designer with the "Insert JSON..." button (IWMAC Designer Import/Export
userscript, Panel JSON section under Manage Files). Give this briefing plus
generated-panel-example.json to the AI as knowledge. The complete object
catalogues (reference_data/all-design-objects.json and controls-registry.json)
are optional extra knowledge - the allowlist in section 4 is enough for most
panels.

1. WHAT YOU ARE MAKING
----------------------
A plant-view panel: absolutely positioned objects on a 1400 x 750 canvas.
Objects are either TEXT (headers, labels), VALUE displays (numbers that show a
live reading once linked), STATUS symbols (LEDs, alarm bells, state strips) or
EQUIPMENT icons (fans, pumps, valves, pipes). You lay them out and describe
each signal in alias_text. A HUMAN links each object to a real driver
afterwards inside the designer - you NEVER invent driver ids.

2. THE OUTPUT FILE - EXACT SHAPE (NORMATIVE)
--------------------------------------------
Reply with RAW JSON only. No markdown fences, no comments, no trailing text.

{
  "format": "iwmac-designer-panel",
  "version": 1,
  "generator": "your-agent-name",
  "source_plant_id": "PLANT_ID_OR_EMPTY",
  "panel_name": "PanelName",
  "panel_width": "1400px",
  "panel_height": "750px",
  "counts": { "single_objects": N, "containers": 0, "graphics": 0 },
  "background_embedded": false,
  "panel": {
    "plant_id": "PLANT_ID_OR_EMPTY",
    "panel_name": "PanelName",
    "panel_width": "1400px",
    "panel_height": "750px",
    "org_image_name": "",
    "image_name": "",
    "saved_by": "copilot",
    "single_objects": [ OBJECT, OBJECT, ... ],
    "containers": [],
    "graphics": []
  }
}

counts.single_objects MUST equal the real array length. counts.containers
is 0 and panel.containers stays [] in every panel type EXCEPT list panels
(section 7c), where each table row is a container and counts.containers
MUST equal that array's real length.

BACKGROUND ARTWORK (optional) - three ways, in priority order on insert
(picked file beats image_svg beats image_data):

1. YOU CAN DRAW IT YOURSELF (v1.2.0+): put raw SVG markup in the panel
   object as "image_svg". Rules: the string starts with <svg, carries
   viewBox="0 0 1400 750" (match the panel size), NO <script> tags, and
   its coordinates line up with your object positions (same pixel space).
   Insert validates it, converts it to a data-URL and embeds it as the
   background - so one file delivers artwork AND objects.
   What to draw (keep it schematic, like the production PNGs):
   - a light page background (#eef1f4-ish) and a tinted side/section zone
   - a rounded-rect aggregate/machine enclosure with a small title text
   - soft duct-band shadows BEHIND where your pipe objects run
     (supply tinted blue, extract tinted warm), airflow arrows
   - dashed zone boxes (VGV cross-over, coil sections)
   Never cover the canvas in dark colors, never draw values or symbols the
   OBJECTS already provide (no fake numbers, LEDs or fans in the SVG).
2. If the user supplies ready image data, put it in "image_data" as a
   data:image/png;base64,... string with "converted": "true".
3. If they only have a file on disk, leave the fields out - the Insert
   dialog's background picker (v1.1.0+) embeds it for them.
Set the envelope's "background_embedded": true when 1 or 2 is used.

READING THE EXISTING DRAWING: "image_svg_trace" (v1.5.0). Exported panel
jsons MAY carry panel.image_svg_trace - an automatic VECTOR TRACE of the
panel's current raster background (or the SVG itself when the background
was SVG). It is INPUT FOR YOU, never output:
- READ it to learn how the drawing is structured: the path coordinates
  tell you where the pipe runs, vessels, frames, side panels and section
  boxes sit - the geometry the plain PNG cannot tell you. Since v1.5.1
  the path fills are the drawing's REAL colours (palette derived from the
  image), and colour is meaning in these schematics: orange = hot
  gas / discharge, blue/cyan = suction, yellow = liquid, green = OK /
  running, red = alarm. Use the fill colours to tell the circuits apart.
- USE that structure when asked to generate or modify artwork: author
  your OWN clean image_svg whose layout matches the traced geometry
  (same runs, same enclosure positions), drawn with crisp shapes.
- NEVER copy image_svg_trace into image_svg or echo it back: traced art
  has thousands of ragged paths and text as outline blobs - it is a map,
  not a drawing. Insert ignores/strips the field; the embedded image_data
  always remains the real background.

3. THE OBJECT ENTRY - COPY THIS TEMPLATE EXACTLY
------------------------------------------------
Change ONLY: obj_id, name index, posWidth/posHeight/posLeft/posTop, tag_text,
alias_text. Everything else stays literally as written here:

{
  "obj_id": "number_v3_value_only",
  "name": "object_0",
  "id": "driver_id",
  "posWidth": 50, "posHeight": 20, "posLeft": 100, "posTop": 100,
  "zIndex": "default",
  "tag_text": "",
  "linked": "false",
  "link_name": "", "link_tag": "", "sub_group": "",
  "driver_id": "driver_id",
  "unit_id": "", "unit_ref": "",
  "alias_text": "Po MT suction pressure"
}

- name: "object_0", "object_1", ... sequential (renumbered on insert anyway).
- driver_id: ALWAYS the literal string "driver_id". linked: ALWAYS "false".
- zIndex: ALWAYS "default".
- positions/sizes: plain integers (pixels).

5. LAYOUT RULES
---------------
- Canvas 1400 x 750. Keep everything inside x 20..1380, y 10..730.
  EXCEPTION: list panels (section 7c) overflow on purpose - the real
  production spjeldliste runs rows to y 4646 and content to x 1585 on a
  nominal 1400x750 panel; the plant view scrolls. Only list panels may
  do this.
- Organize in section columns roughly 300 px wide (x = 20, 320, 640, 960).
- Each section: header bar (number_v3_header_grey75, W 260-280) then rows
  every 28-30 px starting ~35 px below the header.
- A value row = label at column x+5 (W 100-150) + value at x+150..180.
- Never overlap objects. Leave 8+ px gaps.
- Title: number_v3_label_12px_bold at top-left; alarm bell top-right (~x 1240).
- TEXT ENCODING: the Insert JSON flow reads files as UTF-8, and production
  panels do contain Norwegian letters, degree signs and m3-superscripts -
  those survive the real pipeline. BUT if your output travels through any
  non-UTF-8 channel (copy-paste through terminals, old mail systems) they
  mojibake. Safe default: plain ASCII ("gr C", "hoyfart", "gasskjoler");
  Norwegian/degree characters are acceptable when the user asks for them.

6. WHAT THE FIELDS MEAN (SO YOU FILL THEM RIGHT)
------------------------------------------------
- tag_text: the visible text of headers/labels, and the small caption on
  "tag_up"/"con_" boxes. Ignored by value_only, LEDs, bells, state strips.
- alias_text: the SIGNAL DESCRIPTION shown to the human who links the object
  (e.g. "Pc discharge pressure", "MT compressor 2 run status"). Set it on
  every value/status/equipment object. Take the names from the source
  document (P and ID sensor names like Po, Pc, Prec, Sgc, Sd, Ss, Shr2).
- containers: empty array EXCEPT in list panels (section 7c), where every
  table row is one objects_container. graphics: always empty.
- No background image: background_embedded false, org_image_name "".

7. RECIPES
----------
CO2 rack overview (from a P and ID): title + alarm bell; one section per
suction group (MT / LT) with a row per compressor (label + green LED +
capacity value + hours value) and an AK-PC state strip; a TRYKK section
(Po / Pc / Prec / Pgc rows); a TEMPERATURER section (Ss / Sd / Sgc rows);
gas cooler section (fan icon + fan % + HV % + GBV % boxes + cond state
strip); receiver section (Prec + temp); heat recovery section (Shr rows).
See generated-panel-example.json - a complete, insert-verified rack overview
generated from Advansor PID 80.0012 (ValuePack 3x2-1R).

Ventilation unit - THE REAL ANATOMY (normative: it is the sanitized real
production panel reference_data/real-vent-panel-example.json, 102 objects
on the 00-blank-sidebar background; generated-vent-example.json is a
simpler verified starter):
- EXTRACT RUN on top, airflow right-to-left: one long
  number_v3_exhaust_pipe_horisontal (stretch posWidth, e.g. 1025), extract
  fan (V3_58px_fan_left_nrm, tag "JV501") and filter_with_diff_press
  (tag "QD501 Pa") ON the run; con_down boxes ABOVE it: "RT502 gr C"
  (exhaust), "RH501 %", "RT501 gr C" (extract); damper con_top BELOW at the
  left end (tag "KA501 %"); arrows for direction; alarm bells NEXT TO the
  component they guard (fan common alarm by the fan, filter alarm by the
  filter).
- SUPPLY RUN below, airflow left-to-right: fresh_pipe (outdoor section,
  left) then supply_pipe; filter (QD401), heating coil number_v3_heater_3_way
  (LV401), el heater (LV402), cooler, supply fan (V3_58px_fan_right_nrm,
  JV401), smoke LED (RY401); con_down boxes above: "RH901 %" + "RT901 gr C"
  (outdoor), "RT402 gr C" (efficiency), "RH401 %", "RT401 gr C" (supply);
  damper "KA401 %" con_top below; motor output "LR401 %" con_top.
- VGV CROSS-OVER between the runs: exhaust_pipe_vertical +
  supply_pipe_vertical (or number_360_vg_rot across both), rotor alarm
  bell, "LX001 %" con_top (rotor speed), recirculation damper "KA502 %".
- COIL DETAIL under the supply run: coil temps RT510/RT520/RT410/RT420
  con boxes, heating/cooling power "SB510 %"/"SB520 %", pump JP410,
  3-way valve symbol.
- RIGHT COLUMN (x ~1150-1390), three header sections:
  "Status og vendere" (Driftsmodus + Systemvender json boxes, A-Alarm red
  + B-Alarm yellow LEDs, Alarmkvittering), "Vifteregulering" (two columns
  of dark SP boxes labeled Tilluft / Avtrekk: Sp. hoyfart m3/h, Sp. lavfart
  m3/h, Sp. nattkjoling m3/h, Min friskluft %, Sp. CO2 ppm) and
  "Temperaturregulering" (Sp. romtemperatur, Maks/Min tilluftstemperatur).
- ROOM SENSORS mid-right: CO2 "RP501 ppm" and room temp "RT600" boxes.
- TAG CONVENTION: tag_text = instrument code + unit ("RT401 gr C",
  "RF401 m3/h", "KA401 %", "QD401 Pa"); codes follow the vent controller
  (RT=temp, RF=flow, RH=humidity, KA=damper, LR=motor, LX=rotor, QD=filter
  pressure, JV=fan, JP=pump, LV=coil/valve, SB=power, RP=CO2, RY=smoke).

7b. HOW PANELS ARE DRAWN TODAY (PRODUCTION CONVENTIONS)
-------------------------------------------------------
Mined from 194 real compiled panels on 59 plants (reference_data/
panel-conventions.json). Follow these so your output matches house style.

Panel inventory per plant (use these names): Oversikt (store floor plan),
Maskin (machine room / rack), Energi (energy meters, small panel),
Ventilasjon 360.NNN (one per ventilation system, keep the system number),
VGV (heat recovery), Waterloop, Kondenssystem. Also seen: Varmesentral /
Varmeanlegg 320.NNN (heating), Torrkjoler, Isvannsystem, Gatevarme,
Tappevann, Kurver, Fordampere Frys/Kjol, and multi-part overviews
(Oversikt del 1 / del 2, Oversikt Plan 1A/1B/2) on big sites. Swedish
stores use Oversikt Butik / Larmoversikt, Danish use Overblik Butik.

Size: three standards in production - 1400 x 750 and 1400 x 755 on newer
plants (755 is the designer's own preset), 1280 x 1024 on the older fleet.
ALWAYS match the plant's existing panels; default to 1400 x 750 for new work.

Containers appear on only 3 of 194 panels and graphics on 0 of 194 - your
output keeping containers/graphics empty IS the house style. The exception
is the LIST PANEL (spjeldliste, section 7c), which is container-built by
design. Older plants
contain legacy V2 object ids (alarm_anim.gif, number6, red_led_small,
sub_page_1); they still render but are NOT modern style - never emit them.

Backgrounds: every FINISHED production panel sits on a custom PNG (floor
plan or schematic) with objects placed on top. You cannot generate that PNG,
so you have two modes:
  MODE A - BLANK PANEL (default): table-style sections on the empty canvas,
  like generated-panel-example.json. Immediately usable.
  (If the user pastes a data:image/... string, embed it per section 2 and
  you get MODE A with real artwork in one file.)
  MODE B - CLUSTER KIT (when the user says the panel will get a background
  image, or gives a list of cooling positions): emit one CASE CLUSTER per
  position, laid out in a tidy grid (90 px column pitch, 90 px row pitch,
  starting x 40 y 60), each cluster labeled via alias_text with its position
  name. The human inserts your file, then drags each cluster onto the floor
  plan. Do not try to guess floor-plan coordinates.

THE CASE CLUSTER (the standard Oversikt pattern, one per disk/rom - 28
occurrences mined across 16 stores; offsets from the cluster's top-left,
all four link to the same case controller; a 3-member variant without the
cooling symbol is also common on freezer rooms):
  V3_R_34px_circular_alarm_nrm   at dx 12, dy 0    (alarm bell)
  number_v3_40px_no_conn_no_tag  at dx 7,  dy 22   (air temperature)
  V3_R_28px_circular_cooling_nrm at dx 10, dy 35   (cooling relay)
  V3_R_28px_circular_defrost_nrm at dx 28, dy 38   (defrost relay)
Footprint ~62 x 66 px. alias_text pattern: "Disk 1 Melk alarm",
"Disk 1 Melk lufttemp", "Disk 1 Melk kjoling", "Disk 1 Melk avriming".

Other production habits: Maskin panels are dominated by bare
number_v3_value_only readings placed over the schematic plus V3_akpc state
strips and an V3_ok_alarm_nrm banner. Energi panels are small (under 12
objects), built from json_obj boxes. Ventilasjon panels are drawn
object-only on the blank template: duct pieces (exhaust/inlet/supply pipes),
fans, filters, and number_v3_R_45px_con_* boxes whose connector lines point
at the duct. Condenser/gas-cooler fans often appear as two fans stacked
vertically 27 px apart.

7c. LIST PANELS (SPJELDLISTE) - MODE C
--------------------------------------
When the user asks for a "spjeldliste" (damper list) or any long tabular
listing, the house style is a full-width TABLE - the one panel type built
from CONTAINERS. Normative reference: reference_data/
real-spjeldliste-example.json (a real production 360.004 Spjeldliste,
plant masked: 383 scaffold objects + 208 row containers, 21 system groups).

SCAFFOLDING (single_objects; the ONE place zIndex is NOT "default" -
layering matters: stripes "3" under container rows 4 under dividers "5"
under text "900"):
- previous_page_tekn_box_no 1570x57 at x 15 y 50, zIndex "155": top banner
  with back navigation. Put number_v3_label_12px_bold_white title labels
  ON it (y ~63) - one per half-table.
- Column headers: number_v3_label_12px_bold at y ~90: Spjeldnr. x 83,
  Romnr. x 259, Prosj. min. m3/h x 330, Prosj. maks. m3/h x 433,
  Erverdi x 555, SP.paadrag m3/h x 614, Spjeldvinkel % x 710; the same
  set repeated for the right half-table at x +780.
- Vertical dividers: number_v3_header_appgrey, zIndex "5", 3 px wide by
  table height (e.g. 3 x 4580) at each column boundary (x 232, 321, 427,
  543, 605, 703 and mirrored right half), and an 11 px one at x 790
  separating the two half-tables.
- Group highlight: ONE number_v3_header_grey50 1570x20, zIndex "3", behind
  the FIRST row of each system group (2 px above the row top).
- Optional dotted row separators: number_v3_label_8px_norm whose tag_text
  is a long run of dots, one per row line.

ROWS - one container per damper, EXACT template (all fields, note zIndex
is a NUMBER on the container but a STRING on items):
{
  "id": "objects_container",
  "unique_id": "custom_0",
  "name": "objects_container_0",
  "type": "container_c",
  "container_type": "objects_container",
  "className": "objects_container",
  "header_footer": [],
  "linked": "0",
  "linked_to": "0",
  "width": 1544, "height": 23,
  "left": 19, "top": 106,
  "zIndex": 4,
  "items": [ ...cell objects... ],
  "title": "Objects Container"
}
unique_id/name index sequential (custom_0, custom_1, ... - Insert renumbers
to avoid collisions). top: first row 106, +20 per row; a new system group
starts at the PREVIOUS ROW's top + 40 (exactly one blank row slot as the
gap - not +40 on top of the usual +20). One group per ventilation system /
building section.

CELLS (container items): number_v3_label_12px_bold 50x20, posTop 3,
zIndex "900", posLeft RELATIVE to the container: 0 = damper tag

8. WORKFLOW AFTER YOU ANSWER
----------------------------
The user saves your JSON as a .json file, opens the IWMAC Designer on the
target plant, creates/loads a panel, clicks Insert JSON..., picks the file,
then double-clicks each object to link it to a real driver (your alias_text
guides that), and finally uses Compile Panel for Plant + Sync. Nothing you
generate can write to the server - a bad file at worst fails validation with
a listed reason.

8b. LINKING (WHEN GIVEN THE DRIVER-PARAMETERS DUMP)
---------------------------------------------------
Normally the human links objects by hand after insert. But if the user
attaches an iw_gen_driver_parameters .sql (a phpMyAdmin dump of the
plant's driver/parameter table - the real ones are several MB, ~7000
rows) and asks you to link a panel json, you can fill the links in.

THE DUMP: one row per parameter. Columns that matter:
- driver_id: the FULL parameter string (e.g. NNNNN_OJEXHAUST_OJ_1_1_0_4_19).
  This exact string goes into the panel object's driver_id. COPY IT
  VERBATIM - never construct or edit one (the digit groups differ per
  driver type; on the OJ vent driver _4_ = Analog values and _2_ =
  Digital IO, but AKC/EM drivers use other group digits).
- unit_id + unit_name: the unit ("V01" / "360.001 Ventilasjon"). Match
  unit_name against the panel's system number to pick the right unit.
- alias_text: the parameter description ("Actual supply temperature...",
  "Supply motor ON/OFF") - your matching target.
- application: "Analog values" (readings/setpoints) vs "Digital IO"
  (status, alarms) - value boxes need analog rows, LEDs/bells/state
  objects digital rows.
- att: r = read-only, rw = writable (setpoint boxes want rw rows).
- eng_unit (degC, %, Pa, m3/h) and format_extra (enum value map).

PROCEDURE per linkable object:
1. Find the unit: unit_name matches the panel's system (360.001 ->
   "360.001 Ventilasjon") - fixes unit_id and the driver prefix.
2. Find the row whose alias_text matches the object's signal (use the
   object's alias_text/tag_text: "RT401 gr C" -> "Actual supply
   temperature", fan JV401 -> "Supply motor ON/OFF", QD401 -> supply
   filter, alarm bell -> the component's alarm row).
3. Write into the object: driver_id = the row's driver_id (verbatim),
   unit_id = the row's unit_id, linked = "true", alias_text = the row's
   alias_text (production panels show the selector's "Menu,-Description"
   form, e.g. "Most Used,-Actual supply air temperature" - the plain row
   text is accepted).
4. Touch NOTHING else: id stays literally "driver_id", link_name,
   link_tag, unit_ref, positions and obj_id are unchanged.
5. Dummies never link: pipes, connectors, arrows, labels, headers,
   stripes, banner, spjeldliste text cells.
6. Only link matches you are CONFIDENT about. Leave uncertain objects
   unlinked (driver_id "driver_id", linked "false") and tell the user
   which ones you skipped - a wrong link is worse than no link.

RELINKING A WHOLE MACHINE PICTURE (Maskin). A common request: "link out
all the parameters on this machine picture with this dump and give me
the updated json". Machine panels are drawn from a shared template whose
alias_texts ARE the Danfoss parameter names verbatim ("Pc", "Sd-MT",
"Running capacity MT", "C2 LT capacity", "Cond. requested cap.",
"Hr pump speed") - a production cross-check resolved 64 of 64 objects by
EXACT alias-to-alias string match. So:
1. Find the pack unit in the dump (unit_name like "AK-PC782AB-041x";
   it holds Pc/Pgc/Prec/Running capacity). Most objects link there;
   room/gateway leftovers (e.g. "u17 Ther Air") live on an IO unit.
2. Per object: exact-match its alias_text to a dump row's alias_text
   (prefer the pack unit). Same alias twice on the panel = same row.
3. Write the row's driver_id + unit_id, linked "true"; everything else
   stays byte-identical - and reply with the COMPLETE updated json.
4. Report every alias you could not match; leave those unlinked.
5. Cross-plant: parameter-group numbers differ per plant - NEVER carry
   ids over from another plant; the alias names are the portable part.
The canonical 64-signal map (alias -> obj_id + parameter group anatomy
763=MT block / 764=LT / 230+i=Ci status / 240+i=Ci capacity / 337=VSD):
reference_data/maskin-akpc-link-map.json.

Normative pair in reference_data/: real-vent-panel-linked-example.json
(the linked twin of real-vent-panel-example.json - diff them to see
exactly which four fields change) and driver-parameters-sample.sql (the
dump format, trimmed). Driver ids are plant-prefixed: always link from
the TARGET plant's dump.
